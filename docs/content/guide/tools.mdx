Everything Tuimark renders can be printed as data. The CLI commands on this page all build the same frame the terminal would show, deterministically, and never read the environment, so their output is the same on every machine and in CI. That is what makes them useful to an agent, to a test, and to you.

## dump

`tuimark dump FILE` renders one frame at `--cols` × `--rows` (80 × 24 by default), with `--data FILE.json` as the store. The text form has three sections: the grid, the nodes, the diagnostics.

<include cwd lang="tui">snippets/tiny/app.tui</include>

<include cwd lang="term">snippets/out/tiny-text.txt</include>

Each node line is `id tag WxH @(x,y)`, with `-` for a node without an id, and ends with `focus`, `selected`, or `checked` when those apply. The `=== errors ===` section is `ok` or one diagnostic per line.

### The JSON dump

`--format json` is the same frame for a program:

<include cwd lang="jsonc">snippets/out/tiny-json.jsonc</include>

| Field | Holds |
|---|---|
| `cols`, `rows` | the size rendered |
| `ok` | `false` when any diagnostic is an error |
| `focus` | the focused node's id, or `null` |
| `errors` | every diagnostic, warnings included, each with `severity`, `code`, and `msg`, plus `file`, `line`, `col`, `path`, and `id` when known |
| `nodes` | every laid-out node in document order, modals last |
| `grid` | the painted frame: `rows` strings, each exactly `cols` columns wide, no ANSI |
| `wide` | present and `true` when a row holds a wide or multi-code-point character; see `--cells` |

A node has `tag`, its outer rect `x`, `y`, `w`, `h`, and, when they apply: `id`, `text` (a text's content, an input's value), `key` (a row's key), `focused`, `selected`, `checked`, `scroll` (a viewport's offset and extent), and `classes` (version 2 documents). Nodes scrolled out of a viewport are still listed, with coordinates outside it.

The format is versioned and only grows: a new field is optional, and no field changes type or meaning. JSON schemas for it ship in the repository's `schema/` directory.

Exit status: `0` when the frame is `ok`, `2` when it has an error, `1` for a usage or I/O problem.

### --cells

When text has wide characters, a row of `grid` no longer has one character per column. `--cells` adds a per-column map: one entry per cell, row by row, with its cluster (`""` for the second column of a wide one), its width, and the `id` of the box that painted it.

<include cwd lang="tui">snippets/tiny/wide.tui</include>

<include cwd lang="jsonc">snippets/out/tiny-wide.jsonc</include>

Index `cells` by column whenever `wide` is `true`. The same map decides which node a mouse click lands on.

### --styles

The grid shows characters, not colors. `--styles` (JSON only) adds the effective `theme` and, per row, the runs of cells that share a foreground, background, and attributes:

<include cwd lang="jsonc">snippets/out/tiny-styles.jsonc</include>

Colors are exact: `#rrggbb`, an ANSI name, or `default`. `a` lists `bold`, `dim`, `italic`, `underline`, and `reverse` when set. This is how a test checks that `:focus` or a theme token actually changed a cell, by diffing JSON instead of reading ANSI by eye. Add `--theme light` to check the other palette.

## play

`tuimark play FILE` replays input against a document with no terminal: the same key decoding, key handling, focus, and event rules as a running app. It prints the final frame plus every action that fired.

<include cwd lang="jsonc">snippets/out/hello-play-json.jsonc</include>

Steps come from `--input "STEP STEP …"` (separated by spaces) or `--script FILE.ndjson` (one JSON object per line):

| `--input` step | `--script` line | Does |
|---|---|---|
| `enter`, `q`, `ctrl+a`, `shift+tab`, … | `{"key": "enter"}` | one key: a [key token](/reference/keys) |
| `text:deploy` | `{"text": "deploy"}` | typed text; a run of characters into an input is one edit |
| `paste:STR` | `{"paste": "…"}` | one bracketed paste; it never reaches the keymap |
| `set:PATH=JSON` | `{"set": {"path": "…", "value": …}}` | `Set(PATH, value)` from the host |
| `focus:#id` | `{"focus": "#id"}` | `Set("@focus", "#id")` |
| `set:@theme="light"` | `{"theme": "light"}` | the host's theme |
| `resize:100x30` | `{"resize": [100, 30]}` | the terminal is resized |
| `tick:DUR` | `{"tick": "DUR"}` | advances the virtual clock by `DUR` (`250ms`, `1.5s`, `1m30s`), which turns a [spinner](/guide/widgets#the-spinner) and fires a Go host's `Every` |
| `click:X,Y` | `{"click": [X, Y]}` | a left click at a cell (version 2, mouse on) |
| `wheel-up:X,Y`, `wheel-down:X,Y` | `{"wheel": "up", "at": [X, Y]}` | one wheel step at a cell |

- Host actions are recorded, never run. A `set:` step stands in for what a handler would do, so a whole interaction can be scripted: `--input "enter set:confirm_open=true tab enter"`.
- `quit` ends the session; later steps are skipped.
- `--format json` adds `"events"`, each `{step, action, source, keys, value}`; `--frames` adds one settled frame per step. `--styles` and `--cells` work as for `dump`.
- A step that cannot be applied (an unknown key, a click outside the grid, a bad path) exits 1 and names the step on stderr.

## inspect

`tuimark inspect` answers "why does this look like that?" for one node. Pick it by id, or by a cell with `--at X,Y`, the node a click there would start from:

<include cwd lang="term">snippets/out/hello-inspect.txt</include>

It prints the node, its layout path, and its pseudo-classes, then one line per property that is not at its initial value: the computed value, where it came from (`ua` for the built-in sheet, `attribute`, `author`, `inline`, or `inherited`), the winning rule with its file, line, selector, and specificity, and the rules it overrode. `--json` prints the same as JSON, plus every class the node could have, with the guard behind it and whether any rule uses it: the quickest way to find a class that no selector matches.

When the document is built from [fragments or templates](/guide/composition), the output ends with where the node came from: a `source` line with the file, line, and column of the element it was built from, then one `via` line for each `<use>` or `<include>` that placed it, innermost first. In `--json` these are the `source` member, `{"file", "line", "col", "via": [...]}`, with `use` and `template` (or `include`) in each `via` entry. A node the document wrote itself has no `via` line, and a document that writes `version` has no `source` at all.

## validate

`tuimark validate FILE` reports every diagnostic without printing a frame. It checks the whole document, including other screens, closed modals, and false `if` branches, and lays it out at 40, 80, and 120 columns to find layout problems at the sizes that matter (under both themes, for `theme="auto"`).

```sh
tuimark validate app.tui                          # parse and style checks
tuimark validate app.tui --data sample.json       # plus every path against the data
tuimark validate app.tui --strict                 # missing paths become errors
tuimark validate app.tui --catalog actions.json   # unknown action names become B004
tuimark validate app.tui --json                   # diagnostics and the action catalog as JSON
```

Bind checks need data: without `--data`, every path would read as missing, so they are skipped, and the text output ends with `ok (bindings not checked: no --data)` instead of `ok`. With `--data` the line stays `ok`, and warnings are still printed before it. `--json` has the members `actions`, `data`, `diagnostics`, `file`, and `ok`, where `data` is the `--data` argument as given, or `null` without it. `--catalog` takes a JSON array of action names, or `{"actions": [...]}`.

`validate` also takes a [fragment](/guide/language#composing-a-document-from-files). It checks that one file with the checks its elements give themselves (tags, attributes, units, ids), reads no file its `<include>` elements name, and ends with `ok (fragment checked on its own)`, with or without `--data`, since the data and the uses live in the documents that include it. The flags that change what is checked (`--strict`, `--catalog`) have no effect on it; a bad `--theme` or an unreadable `--catalog` is still a usage error (exit `1`).

## catalog

`tuimark catalog` prints the closed vocabulary as one JSON object: every tag with its attributes (and an enumerated attribute's keywords), every CSS property with its syntax and keywords, the pseudo-classes, the `@media` features, the key tokens, the built-in actions, and the diagnostic codes. On every item, `since` is the lowest document version that accepts it. It is generated from the runtime's own tables, takes no flags, and reads no environment variable, so an editor or an agent can read it instead of scraping `AGENTS.md`. `catalog` is the format version (1): adding members, items, or versions keeps it.

```sh
tuimark catalog | jq '.tags[] | select(.name == "list") | .attrs[] | select(.since > 1)'
```

## new

`tuimark new NAME [--go | --ts]` creates a project in the directory `NAME`, which must not exist or must be empty. It writes `app.tui`, `theme.tcss`, `sample.json`, and `AGENTS.md` (the briefing `tuimark agents --project` prints); `--go` adds `main.go` and `go.mod`, and `--ts` adds `parent.ts` and `package.json`. No file is ever overwritten, and a usage error writes nothing. It prints the files and the command that runs the project, such as [`tuimark run`](/guide/run).

```sh
tuimark new todo
cd todo && tuimark run app.tui --data sample.json
```

<Callout type="info" title="--ts and npm">

A `--ts` project depends on [`@thelacanians/tuimark`](/guide/typescript), which runs the `tuimark` binary of its own release. To work on the client itself, install the copy in a clone of the repository instead: `bun add @thelacanians/tuimark@file:/path/to/tuimark/sdk/ts`.

</Callout>

## preview

`tuimark preview FILE` prints the text dump and, when stdout is a terminal, paints the frame with ANSI colors first. `--watch` repaints whenever the document, its stylesheets, the fragments it includes (at any depth), or the data file change. `--color truecolor|256|16|none` picks the color depth; otherwise it follows `TUIMARK_COLOR`, then the terminal's own capabilities.

## fmt

`tuimark fmt FILE` prints the document in canonical form; `--write` rewrites it and `--check` exits 2 when it is not formatted. See [formatting](/guide/language#formatting). It formats a fragment exactly as it formats a document, with `<fragment>` as the root, and never reads the files its `<include>` elements name; `--write` rewrites only the file you named.

## ir

`tuimark ir FILE` prints the parsed document as JSON: every node with its attributes, bindings, actions, and its own inline style, before any stylesheet is applied, plus the keymap and the resolved theme tokens. It is the document's structure as the runtime understands it. A schema for it ships in `schema/`. For a document built from [fragments or templates](/guide/composition#seeing-what-a-copy-produced), the root tree keeps the composition as written: an `include` or `use` node holds what it placed, and each placed node has a `from` member, `FILE:LINE`.

## Composition in the tools

A document built from [fragments and templates](/guide/composition) is expanded when it is read, so `dump`, `play`, `validate`, and `test` work on the expanded document with no flag. The commands that say more, or that act on a fragment:

- **`inspect`** names the element a node was built from and every use and include that placed it (above).
- **`validate`, `fmt`** accept a fragment (above). Every other command that renders (`dump`, `play`, `preview`, `inspect`, `ir`) refuses one with `V005` and exit `2`, since a fragment has no screen: check it through the document that includes it. `inspect` writes that error to stderr and nothing to stdout:

<include cwd lang="term">snippets/out/tpl-inspect-fragment.txt</include>

- **`run` and `preview --watch`** watch the fragments the document includes, at any depth (the ones a template includes too), as well as its stylesheets and data. Saving any of them reloads once. A fragment that does not exist yet is watched, so creating it reloads, and while the document does not parse, saving a fragment still reloads. See [reload](/guide/run#reload).
- **`tuimark mcp`** gives the same results: `tuimark_validate` on a fragment returns its JSON with `"ok": true` and no diagnostics, and `tuimark_inspect` on a fragment returns the `V005` text above as its result, as data, not as `isError`.

## Editor support (tuimark lsp)

`tuimark lsp` is a [Language Server Protocol](https://microsoft.github.io/language-server-protocol/) (3.17) server on stdin/stdout for `.tui` and `.tcss` files, so an editor shows what `validate` says as you type. It takes no arguments, uses only the standard library, and reads no environment variable. The VS Code extension starts it from `PATH`, and any editor with an LSP client can run `tuimark lsp` as a stdio server for the two file types. [Editors](/guide/editors) shows how to set it up in VS Code, Neovim, and Helix.

What it offers:

- **Diagnostics.** The checks `tuimark validate` runs, with the same messages, codes, and severities (error and warning), under both themes for a `theme="auto"` document. A diagnostic in a stylesheet shows on the stylesheet, not on the `.tui` that loads it: the server reads each `<style src>` as `Load` does (`..` included) and sends a diagnostic to the file it is in. It sends them after you open or change a file, at most once every 150 ms per file.
- **Your unsaved text.** A document is checked as the editor has it, and so is a stylesheet it loads when that stylesheet is open too; one that is not open is read from disk.
- **Bindings.** A `sample.json` next to the `.tui` is used as if you had passed `--data`, so `B001` to `B003` and `B008` to `B010` appear. Without one they are skipped, as `validate` skips them without `--data`, and the same goes for a `sample.json` that is not valid JSON.
- **Completion.** In a `.tui`: tag names, the attributes of the tag, the keywords of an enumerated attribute, `#id` targets for `to`, `when`, and `focus`, action names (the built-in ones and the ones the document already uses), key tokens in `keys`, and the paths of `sample.json` in `{path}`, `each`, `bind`, and `if`. In a `.tcss`: property names and their keywords, `$tokens`, pseudo-classes, `@media` features, and the `#id`s and `.class`es of the documents that load it. Everything is filtered by the document's `version`; a stylesheet takes the newest version among the documents that load it.
- **Hover.** The catalog entry of the tag, attribute, property, keyword, or diagnostic code under the cursor: its value syntax or keywords, and the version that introduced it.
- **Go to definition.** An `#id` (in a selector, `to`, `when`, or `focus`) goes to its element, a `.class` to every element that has it, `<style src>` to its file, and a `$token` to where `:root` declares it.
- **Fragments and templates.** A fragment gets the diagnostics the documents that include it give its file, found among the open documents and the `.tui` files of its directory and its parent; a fragment no document reads is checked on its own, with no `V005`. Go to definition follows `<include src>`, `template="…"`, and a scoped `#id` (`#billing__street__input`) across files, and a use's `#id` goes to the `<use>`. Completion in `template=` offers the document's templates, and the `#id` targets (`to`, `when`, `focus`) add the scoped ids of every copy. A fragment is formatted as `tuimark fmt` formats it. A pinned document keeps the older behavior: no `template=`.
- **Formatting.** For a `.tui`, one edit with what `tuimark fmt` prints; none when the file is already formatted or is not well-formed XML. A `.tcss` has no formatter.

A stylesheet is "loaded by" every open `.tui` that names it, and every `.tui` in its directory that does. Rename, code actions, semantic tokens, and workspace symbols are not offered. Positions are the protocol's: a 0-based line and a UTF-16 offset, converted from the 1-based line and code-point column `validate` prints. The server exits 0 on `exit` after `shutdown` (or when its input ends after one), and 1 otherwise.

## Environment variables

Only a running app (`Run()`, and the [`tuimark run`](/guide/run) and `tuimark host` sessions built on it) and `preview` read the environment. The tools above never do.

| Variable | Values | Effect |
|---|---|---|
| `TUIMARK_THEME` | `dark`, `light` | overrides the theme, like `--theme` |
| `TUIMARK_COLOR` | `truecolor`, `256`, `16`, `none` | forces the color depth instead of detecting it from `TERM`, `COLORTERM`, `NO_COLOR`, and friends |
| `TUIMARK_SYNC` | `0`, `1` | turns synchronized output off or on instead of asking the terminal |
| `TUIMARK_LOG` | a file path | writes an NDJSON log of the session |
| `COLORFGBG` | set by some terminals | the fallback for `theme="auto"` when the terminal does not answer the background query |

Values are exact; an empty value counts as unset. An invalid value makes `Run` return an error before it touches the terminal.

### TUIMARK_LOG

A running app owns the terminal, so it cannot print diagnostics there. `TUIMARK_LOG=session.ndjson ./myapp` writes one JSON object per line instead: the start, the terminal's capabilities and the resolved theme, then every key, paste, mouse event, action, frame (with how long it took and how many bytes it wrote), and resize, and finally why it ended.

```sh
TUIMARK_LOG=session.ndjson ./myapp
jq -c 'select(.ev == "action")' session.ndjson
```

The file is created with mode `0600`. While a `secret` input has focus, keys and pastes are logged as redacted, and that input's events never carry its value.
