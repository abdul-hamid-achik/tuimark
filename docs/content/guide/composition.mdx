A document that grows has two problems: it gets long, and the same few lines appear again and again. The current language (a `<tui>` without `version`) has a tool for each, and both are expanded when the document is read, so nothing about them exists at run time. The dump, the keymap, focus, and the events see the expanded document, as if you had written every copy by hand.

| You want | Use | Result |
|---|---|---|
| to split a long document by the pieces a person would name | [`<include>` and `<fragment>`](/guide/language#composing-a-document-from-files) | the contents of a file placed where the include stands |
| to repeat a piece, each time with its own data | `<template>` and `<use>` (this page) | a copy of the template at every `<use>`, with scoped ids and its data behind an alias |
| to vary the text of each copy: a title, a label, a width, a variant | [props](#props) | `{$name}` in the template, replaced by the text each `<use>` passes |
| to put markup you write at the use inside the copy | [the slot](#the-slot) | the content of a `<use>`, placed where the template's `<slot/>` stands |

Includes and templates combine: a fragment can hold templates, so a team keeps its form fields in one file and every document includes it. A pinned document (one that writes `version="1"`, `"2"`, or `"3"`) has none of these tags; they are `V001`, "requires a `<tui>` without version".

## A template and its uses

A `<template id="…">` holds a piece of markup. It is never drawn by itself. Each `<use template="…"/>` places a copy of it where the `use` stands:

<include cwd lang="tui">snippets/templates/field.tui</include>

`field` has a label, an input, and an error line, and the form uses it twice. Each `<use>` names its template, gives the copy an `id`, and says which data the copy reads with `with`. Both fields come out of the same markup:

<include cwd lang="grid">snippets/out/tpl-dump.txt</include>

- **Where a template stands.** As a direct child of `<tui>` or `<screen>`, in the document or in a fragment it includes; anywhere else is `V001`. It may stand before or after the uses that name it. Its `id` is required (`V012`) and unique among templates (`V004`).
- **What it holds.** Any elements, one or several. Not `<tui>`, `<screen>`, `<style>`, `<keymap>`, `<bind>`, `<fragment>`, or another `<template>` at any depth (`V001`), and no loose text (`V013`: wrap it in a `<text>`). A template can hold `<use>` elements of other templates, so a template can build on a smaller one, and one `<slot/>` ([below](#the-slot)).
- **What a `<use>` takes.** `template` (required), `id`, `with`, `if`, `hidden`, a static `class`, and the [props](#props) its template declares. Any other attribute is `V002`, and the message says where it goes instead: on the template's element, as a class, or (for a name that could be a prop) in the template's `props`. The content between `<use>` and `</use>` fills the template's [slot](#the-slot); content for a template that has no slot is `V013`.
- **What a copy is.** The same elements as the template, built where the use stands, checked as if you had written them there. A `<use>` is not a node: it takes no space in the layout, and `to="#email"` naming one is `B005`.

## Scoped ids

Two copies of one template cannot both have an input called `input`, so a copy's ids are prefixed with the id of its use and two underscores: the input of `<use id="email">` is `email__input`. This is the same `instance__part` shape the [kit](/guide/kit#conventions) uses for its ids, and it is what your own references use:

<include cwd lang="term">snippets/out/tpl-ids.txt</include>

- **Outside the copy, write the scoped id.** The keymap row `<bind keys="ctrl+n" action="focus" to="#email__input"/>`, the screen's `focus="#name__input"`, a stylesheet rule `#email__input { … }`, and `play`'s `focus:#email__input` all name the copy's element. The host sees the scoped id too: the `source` of an event is `email__input`, and a host that routes by the part before the last `__` gets `email`.
- **Inside the copy, write the id as the template has it.** In a template, `focus="#no"` on a modal means the `no` button of the same copy, and each copy resolves it to its own: `del__no` for `<use id="del">`.
- **A reference to the unscoped id from outside is `B005`**, and the message names the one you want:

<include cwd lang="tui">snippets/templates/ref-bad.tui</include>

<include cwd lang="term">snippets/out/tpl-ref-bad.txt</include>

- **A use needs an `id` when its template has ids** (`V012`: the message lists them and the scoped form they take). A template with no ids can be used without one.
- **Nesting adds a prefix.** A template that uses another one scopes the inner ids by both uses: `billing__street__input` below.
- **A use's id is an id of the document**, so it must not repeat another (`V004`). A copy's ids never clash with another copy's.

A confirmation dialog is a good template, because its ids, the modal's `focus`, and its keys all stay inside the copy. Here the keymap row reaches the copy's modal by its scoped id, and `y`, `tab`, and `enter` act on it:

<include cwd lang="term">snippets/out/tpl-confirm-events.txt</include>

The `y` row fired with `del__no` as the source, the button the modal's `focus="#no"` selected; then `tab` and `enter` clicked `del__yes`. Pressing `esc` would close the modal, because `open="c.open"` is a path the runtime can write through the alias.

## What `with` does

`with="path as alias"` makes `alias` stand for `path` inside the copy. Every path in the copy that starts with the alias goes to that path in the store: `{f.label}` reads `form.email.label`, and `bind="f.value"` reads and **writes** `form.email.value`. That is why the typed text above reached `form.name.value`. Nothing is copied; the alias is a name for the path, so an input in a copy edits the same data a `{form.name.value}` anywhere else shows.

- **Several clauses** are separated by exactly a comma and a space: `with="form.one as x, form.two as y"`. Anything else is `V011`, as is an alias written twice in one `with`.
- **The target may not exist yet.** An input in the copy creates the path when you type. The use reports one `B003` for the missing path, and nothing more from the copy (see [a missing `with` path](#a-missing-with-path-and-optional-flags)).
- **Nested uses compose.** In `parts/forms.tui` below, `address` reads `a.street` and passes it on as `f` to `field`; the input ends up bound to `order.billing.street.value`.
- **A copy sees the aliases in scope where its use stands.** A use inside a list row or an `each` container can read the row's alias without being given it, and a `with` path can start with it: `with="j.status as s"`. The template then depends on where it is used, so give a reusable template a `with` for everything it reads.
- **An inner `each` can reuse the name of a use-site alias.** In the template, `each="g.items as r"` shadows the `r` of the surrounding list while the copy is built, and `g` still reads through `with="r.group as g"`. An inner `each` alias that repeats a `with` alias, though, is `V011` at that element. The copy is still placed.

## Guards and classes on a use

`if` and `hidden` on a `<use>` decide whether its copy exists in the frame, and they are read **where the use stands**: the `with` of the same use is not in scope for them (`if="s.urgent"` would read a path the use itself defines, which is `B002`), but an `each` alias is. ## Props

`with` passes data: a path the copy reads, and writes. A **prop** passes text: a title, a label, a width, a variant, the name of an action. The template declares its props with `props="…"`, a `<use>` passes each one as an attribute with that name, and the template's body reads it as `{$name}`:

<include cwd lang="tui">snippets/templates/props.tui</include>

`stat` declares four props. Each `<use>` passes its own title, max, and style (a width), and the CPU one a `tone` too; `with` still brings the numbers:

<include cwd lang="grid">snippets/out/tpl-props-dump.txt</include>

A prop is replaced when the document is read, before any data, so it costs nothing at run time and never changes while the app runs. The dump shows the copy as substituted, `class="{$tone}"` included:

<include cwd lang="jsonc">snippets/out/tpl-props-classes.jsonc</include>

Only the CPU box has a class. The Memory `<use>` passes no `tone`, so its box has no `class` attribute at all.

- **Declaring.** `props="title max"` lists the names with exactly one space between them and none before the first or after the last. A name is lowercase letters, digits, `_` and `-`, starting with a letter or `_` (the same rule as a `class:NAME`). `props=""`, or no `props`, declares none. A name a `<use>` keeps for itself (`id`, `template`, `with`, `if`, `hidden`, `class`) cannot be a prop. Each mistake is `V003` at the `props` attribute.
- **Passing.** A prop is the literal text of an attribute, taken as written. `title=""` passes the empty string, which is a value. A prop the `<use>` does not write is *not passed*. Any other attribute on a `<use>` is `V002`, and for a name that could be a prop its message tells you to declare it.
- **Where `{$name}` may stand.** In the text of a `<text>`, a `<button>`, or a `<column>`; in the attributes that take a `{path}` template (`title`, `placeholder`, the `label` of a button, checkbox, select, or tab, and a tab's `short`); and in the attributes whose value is literal: the sizes `width`, `height`, `gap`, and `pad`, and `border`, `min`, `max`, `mark`, `value`, `wrap`, `axis`, `priority`, `scale`, `class`, `style`, and the action name of an `on:*` attribute (`on:click="{$action}"` fires the name the `<use>` passed). Several may share a value with literal text or `{path}`: `class="stat {$tone}"`, `style="width: {$w}"`, `title="{$label}: {f.value}"`.
- **Where it may not.** In an attribute that takes a path (`bind`, `each`, `key`, `checked`, `if`, `hidden`, `disabled`, `open`, `class:NAME`, a `<use>`'s `with`), in an `id` or a `#id` reference such as `focus`, in a `<use>`'s `template`, in an `<include>`'s `src`, in `focusable`, `secret`, `single`, and the other attributes the list above does not name, and anywhere outside a template's body. Each is `V003` at that attribute. Inside a template the attribute is then ignored, in the template and in every copy; outside one the value stays as written. A name inside braces, as in `{f.{$k}}`, is `V003` too.
- **A prop that is not passed.** When the attribute's whole value is exactly `{$name}`, the attribute is not in the copy at all, as if the template had not written it: `<sparkline min="0" max="{$max}"/>` copied without `max` takes its range from its values, and `class="{$tone}"` writes no class. Anywhere else the prop is the empty string: `title="{$title}: total"` becomes `: total`. "Whole value" is exact: `max=" {$max}"` has a space around it, so it becomes `max=" "`, which is then checked as written. So a prop is optional unless the template needs it.
- **Props are text, never data.** The value of a prop does not become a `{path}`: a pair of braces that a value brings is `V003`, and the prop is not passed in that copy. Write data with `with`. A lone `{` or `}` stays literal text. Substitution is one pass, so the text a prop brings is never read as another `{$name}`.
- **A substituted value is checked as if you had written it.** `max="lots"` is the bad-`max` `V003`, and `border="wavy"` the bad-`border` one, at the template's attribute, and the message ends with the `<use>` that wrote the bad text.
- **Passing a prop on.** A `<use>` in a template's body may pass that template's props to its own template: `<use template="field" label="{$label}"/>`. When the outer `<use>` does not pass `label`, that attribute is not in the inner `<use>`, which then does not pass it either. A `<use>`'s `class` may hold a prop (`class="{$tone}"`).
- **Size a copy with a `style` prop.** A template root that declares `style` and writes `style="{$style}"`, as `stat` does, lets each `<use>` size its own copy, and a copy whose `<use>` passes none writes no `style` at all. The [kit](/guide/kit) does this in its components.

The mistakes are reported where they are made. This document makes four of them:

## The slot

A template that wraps something, such as a panel, a dialog, or a card, cannot know the markup its users want inside. A `<slot/>` in the template marks where it goes, and each `<use>` writes that markup between its tags:

<include cwd lang="tui">snippets/templates/slot.tui</include>

The `<input>` and the `<text>` are written in the `<use>` and land inside the `panel`'s column, where the slot stands. Typing into the input writes `note`, and the text reads it:

<include cwd lang="grid">snippets/out/tpl-slot-typed.txt</include>

- **One slot per template**, with no attributes and no content. A second `<slot/>` in one template is `V019`, and there is no fallback content: a `<use>` that writes nothing leaves the slot empty (and a parent whose only element is the slot is `:empty`).
- **The content belongs to the place where you wrote it.** It is built as if you had written it where the `<use>` stands, and then placed at the slot. So its paths are the document's: `{user.name}` and `bind="note"` above read the store as they would without the `<use>`, and neither the `with` aliases of the `<use>` nor the `each` aliases of the copy are in scope in it (an alias of the place where you wrote it, such as a list row's, still is). Its `#id` references mean the elements written there. A static `class` on the `<use>` does not reach it. A `{$name}` in it reads the props of the template it is written in, if it is written in one.
- **Its ids are not scoped by the use.** The input is `note`, not `side__note`, and the keymap row names it `#note`. The template's own ids are scoped as ever, so the column is `side__frame`:

<include cwd lang="term">snippets/out/tpl-slot-ids.txt</include>

  An id in the content is an id of the document like any other, so repeating one is `V004`. It does not count toward the `<use>`'s need for an `id` (`V012`), which only the template's own ids set off.
- **Includes in the content** look for their `src` next to the file where the content is written, not next to the template's file. A fragment that includes itself through a `<use>`'s content is `V006`, as for any include cycle.
- **It stands where the slot stands.** The focus order, the cascade, and the dump see it there, and the parent it lands in decides what may stand there: `tab` elements fill a slot that stands in a `<tabs>`, and a `tab` anywhere else is `V016`, as if you had written it there. When the `<use>`'s `if` or `hidden` removes the copy, the content goes with it.
- **Where a slot may stand.** Directly in the template, in a container, a `modal`, a `tab`, a `tabs`, a static `list` (one without `each`), or in the content of another `<use>` in the template. Not inside a list `<item>`, not inside the template of an `each` container, and not directly in a `<table>` or a `<list each=…>`: each is `V001`, because their content repeats per row and would need the row's alias. A table's columns or a list's rows cannot come from a slot.
- **Content is elements.** Text written directly in a `<use>` is `V013` ("wrap it in `<text>`"), and a `tui`, `screen`, `style`, `keymap`, `bind`, or `template` in the content is `V001`. Content for a template with no slot is `V013`: `<template id="T"> has no <slot/>`.
- **Forwarding.** A template can pass its content on to a smaller one by putting its own `<slot/>` in the content of the inner `<use>`. The content keeps the meaning of the place where the outer `<use>` is written, through any number of templates, and the template can write its own elements around the slot:

<include cwd lang="tui">snippets/templates/slot-forward.tui</include>

<include cwd lang="grid">snippets/out/tpl-slot-forward.txt</include>

`note-panel` adds its `Notes` line above what its user wrote, and `panel` draws the frame. The `{user.name}` still reads the document's store.

The mistakes of the slot, each at the place that makes it:

## Props, `with`, or the slot

Three ways to hand something to a copy, for three kinds of thing:

| The copy needs | Use | Why |
|---|---|---|
| a title, label, placeholder, size, border, variant, limit, or action name, the same text every time the app runs | a prop | text, replaced when the document is read; it can set the attributes that take a literal value, which no path can |
| a value that changes while the app runs, an array, a flag, or a field the copy writes | `with` | a path into the store, read and written live; the only way to reach `bind`, `each`, `if`, and `class:NAME` |
| elements: a body, a footer, a row of buttons | the slot | markup written at the `<use>`, with that place's ids, paths, and actions |

- **A prop is never data.** `title="{user.name}"` is `V003`. Give the copy `with="user as u"` and read `{u.name}`, or write a `<text>{user.name}</text>` in the slot.
- **A variant is a class or a prop.** For a look the stylesheet owns, put a static `class` on the `<use>`; for one the template spells out, such as a width or a border, pass a prop.
- **They combine.** `stat` above takes its numbers from `with` and its title, max, and width (through `style`) from props; add a `<slot/>` to it and each `<use>` can put a footer inside the box.

## Seeing what a copy produced

The expanded document is what every tool shows, so a copy is checked the way any element is. Three places tell you where it came from.

**The dump.** A copy's nodes appear in the node list with their scoped ids, as in the lists above. `tuimark play` and `dump` need no special flag.

**`inspect`.** Besides the cascade, `tuimark inspect` ends with the element a node was built from and the uses, includes, and slots that placed it, innermost first:

<include cwd lang="term">snippets/out/tpl-split-inspect.txt</include>

The input `shipping__zip__input` was written at `parts/forms.tui:5:7`, placed by the `zip` use inside `address` (line 11), which the `shipping` use placed (`app.tui`, line 6). With `--json` the same information is the `source` member:

<include cwd lang="jsonc">snippets/out/tpl-inspect.jsonc</include>

A node the document writes itself has `"via": []`, and a document that writes `version` has no `source` at all. A use without an `id` is listed as `<use template="…">`.

A node in the content of a `<use>` was written outside the template, so its `via` names the `<slot/>` that received it: for the `note` input of the slot example above, `via <slot/> of <use id="side" template="panel"> slot.tui:4:7`, the line of the slot in the template. In `--json` that entry is `{slot, template, file, line, col}`, where `slot` is the use's id.

**`ir`.** `tuimark ir` keeps the composition as written: a `use` node holds the copy it placed, in the template's own words (`f.value`, `{f.label}`), with the scoped `id` and a `from` member, `FILE:LINE` of the element the node came from. Props are already substituted in each copy (`title` reads `Today`, not `{$title}`), and a copy's `<slot/>` is kept as a `slot` node that holds the content it received. Read the aliases through the `with` of the enclosing `use`:

<include cwd lang="jsonc">snippets/out/tpl-ir.jsonc</include>

`from` is on every node a use or an include placed, and absent on a node the document wrote in its own file. A template's own node in `ir` keeps its `props` and its body as written.

## Diagnostics

The codes a template can raise, with the page's examples where there is one. The [diagnostics reference](/reference/diagnostics) has the full text.

| Code | When |
|---|---|
| `V019` | a `<use>` without `template`, or one that names no template; or one that closes a [cycle](#cycles); a second `<slot/>` in one template |
| `V021` | the [limits](#limits): elements, source bytes, nesting depth |
| `V011` | a `with` that is malformed, repeats an alias, or uses one already in scope; an inner `each` alias equal to a `with` alias |
| `V012` | a `<template>` without `id`; a `<use>` without `id` whose template has ids |
| `V013` | text directly in a `<template>` or a `<use>`; content in a `<use>` whose template has no slot; content in a `<slot/>` |
| `V001`, `V002`, `V004` | a template in the wrong place, or a `<slot/>` where it [cannot stand](#the-slot); an attribute a `<use>` neither takes nor has declared as a prop; a duplicate template, use, or content id |
| `V003` | a bad `props` list; a `{$name}` where a [prop cannot stand](#props), that names no prop, or that is outside a template; a prop that makes a `{path}`; a substituted value that is not valid |
| `B002`, `B003` | a missing `if`/`hidden` path at a use; a [missing `with` path](#a-missing-with-path-and-optional-flags) or a missing path in a copy |
| `B005` | a `to=`, `when=`, or `focus=` that names a use, or names an id only the template writes |

### Cycles

A template that reaches itself through the uses in its body would never stop expanding, so each use on the cycle is `V019`, and none of them expands. A reference to a template that does not exist is `V019` too:

<include cwd lang="tui">snippets/templates/cycle.tui</include>

<include cwd lang="term">snippets/out/tpl-cycle.txt</include>

Each message names a simple cycle through the use, starting from its own template, so the one you read is the loop that use closes. A long one is cut: up to 8 templates are named whole, and a longer cycle shows its first 8, then `… (N more)`, then the template it returns to. A cycle of ten templates reports ten uses, each starting at its own template:

<include cwd lang="term">snippets/out/tpl-long-cycle.txt</include>

A cycle is reported whether or not any use reaches it. One that only copies meet (possible once the template definitions' own `V021` has stopped a body) is reported once, at the use that closes it, however many copies meet it.

### Limits

Because a copy of a copy of a copy grows fast, expansion has a budget, shared with `<include>`. A document that would pass any of these is `V021`:

- **100000 elements** inserted by includes and uses, counted once per copy, at every depth;
- **16 MiB of placed source**, counting the fragments and templates copied, the scoped-id prefixes, and the `with` paths substituted into each copy;
- **256 levels** of nesting in the resulting tree, counting each `<include>` and `<use>` as a level.

The elements of a `<use>`'s content count once for each place a slot puts them, and the text a prop adds to a copy counts as placed source. The use that would go over inserts nothing, and no later include or use expands, so the rest of the document is still reported. Five uses of a template in each of seven templates, one inside another, is 5⁷ leaves:

<include cwd lang="tui">snippets/templates/fan.tui</include>

<include cwd lang="term">snippets/out/tpl-fan.txt</include>

The error is at the use that went over, `t7` in `t6`, with the line and column of that use. A fragment included inside a `<template>` has a budget of its own, so a template whose include would fan out is reported even when no use copies it: the message ends `exceeds the expansion limit for template definitions`, and the template is checked without that include.

### Messages about a copy

An element that a use placed is written once in the template and exists once per copy, so a diagnostic about it is reported at the template's line and has to say which copy it means. There are two forms.

**A path that went through a `with` alias** ends with the path it stands for and the use that gave it: `(P via <use …>)`. In the form below the template reads `f.help` and the use `email` made that `form.email.help`; the `phone` use has no `form.phone`, so the use is the problem, and the copy says nothing more:

A use with an `id` is named by it (`<use id="email">`). A use without one is named by its template (`<use template="badge">`), and when the path starts with an `each` alias, which reads the same in every row, the message adds where the use is written, so you can find it: ` at FILE:LINE:COL`.

<include cwd lang="term">snippets/out/tpl-rows-bad.txt</include>

**Any other diagnostic about a copy** (a `V012` at a copied box, a store flag that is missing) ends with `, placed by <use …> at FILE:LINE:COL`, naming the use that placed the element, and its file, line, and column. A use inside another template is named by its scoped id (`<use id="top__in">`), and its location is the line where it is written in the template. An element placed by an `<include>` ends with `, placed by <include> at FILE:LINE:COL` in the same way.

### A missing `with` path and optional flags

- **A `with` path that is missing is one `B003` at the use**, a warning (an error under `--strict`), as above for `phone`. The copy's own paths are not reported, because each one would say the same thing, so you fix the one line. The copy is still placed, and an input in it still writes the path.
- **A flag in the copy is optional.** When the alias stands for an object, `if`, `hidden`, `disabled`, `open`, and `class:NAME` guards read through it are `null` if the member is missing, without a `B002`: `if="f.error"` is how a form field shows an error only when the host has written one, and `missing.tui` above does not report `f.error`. A `{path}` or a `bind` is still `B003` when missing. When the alias stands for something that is not an object, every flag reports.
- **A store flag is an ordinary one.** A path that does not start with an alias (`hidden="debug"`) is `B002` when missing, once per copy: `, placed by <use id="email"> at …`.

### Long ids and paths

A message quotes at most 64 bytes of an id or a path, cut at a character boundary and followed by `…`, so one very long name cannot make a diagnostic unreadable. Both the path in the copy and the path it stands for are cut, and so is a template name:

## Tools and templates

- [`validate`, `fmt`, `inspect`, `run`, and `preview --watch`](/guide/tools#composition-in-the-tools) know about fragments and copies.
- [The language server](/guide/editors#what-the-language-server-does) checks a fragment through the documents that include it and follows `template=` and scoped ids across files.
- [`play` and `dump`](/guide/testing#documents-built-from-parts) in a test see the expanded document, so a golden does not change when you move a piece into a fragment, as long as the expansion is the same.
- The [kit](/guide/kit#templates-in-your-own-markup) is a fragment of templates: include `kit/kit.tui` once and copy its components with `<use>`.
