# Tuimark

You design terminal UIs by editing text documents. You do not write Go layout.

## Allowed edits
- *.tui
- *.tcss
- examples/**/sample.json

## Forbidden
- internal/**
- cmd/** except flag wiring
- Bubble Tea / lipgloss / tea.Cmd / Update()
- inventing tags not in the catalog

## Catalog
tui style keymap bind screen
col row box scroll spacer
text rule
list item input button progress
modal

Spike-only until dump goldens pass:
app col row box text
attrs: id class width height gap pad border

## Loop
tuimark validate FILE
tuimark dump FILE --data sample.json --cols 80  --rows 24 --format json
tuimark dump FILE --data sample.json --cols 120 --rows 24 --format json
Read grid + nodes. Edit markup or CSS. Repeat.
Stop when 80 and 120 match intent and errors is empty.

## Bindings
{path} only inside <text>, title, placeholder.
each="tickets as item" only on <list>.
if="path" or if="!path".
No expressions.

## Actions
on:select="open" is a name. The host implements it.

Where the frozen lines above and the reference below differ, the reference below wins.

Built-in actions: focus, quit

## Loop, v0.2a addition

The §22 Loop above predates v0.2a and only shows `validate`/`dump`. For a document with an `<input>`, a `<keymap>`, or any `on:` action, extend it with `play` before wiring a Go handler:

tuimark play FILE --data sample.json --input "STEPS" --styles --format json

Read `events` to confirm the right action fired (and with what `keys`/`value`) for the input you replayed; read `styles` (added by `--styles`) to confirm `:focus`/`:selected`/theme-token rules actually change a cell's look, instead of eyeballing `preview`. Add `--theme light` (or `dark`) to check the other theme without touching the document. Repeat `dump`/`play` at 80 and 120 columns as the §22 Loop already does.

## Reference

`tuimark` in the Loop above is `./bin/tuimark` after `go build -o bin/tuimark ./cmd/tuimark`, or `go run ./cmd/tuimark` without building.

`version` on `<tui>` is optional; leave it out. A `<tui>` without it is the current language (tools that need a number for it use 4: the catalog's `current`, `tuimark ir`'s `"version": "0.4"`): everything below applies to it, every rule marked version="2" or version="3" included. A document that writes `version="1"`, `"2"`, or `"3"` is pinned to the meaning it had in tuimark 0.4.1, and the marks matter only there: the newer vocabulary is the diagnostic the mark names, with a message ending in `(requires version=…)`, or in ` (requires a <tui> without version)` for what only the current language accepts. There is no `version="4"`: like any value other than 1, 2, or 3, it is V003 and the document is read as version="1".

The frozen lines at the top are the 0.1 language and predate what this reference documents; they do not forbid what the current language has. `{path}` is not limited to `<text>`, `title`, and `placeholder`: in a `<tui>` without `version` a `<button>`'s body or `label` and a `<checkbox>`'s `label` are templates too, and so is a `<select>`'s `label` (resolved per option) and, in version="3" and the current language, a `<tab>`'s `label` and `short` (the attribute tables and the Notes say where). `each` is also on `col`, `row`, `box`, `table`, and `select`. The 17 tags of `## Catalog` are the version="1" list: the tags the attribute tables below list (`checkbox`, `select`, `include`, `fragment`, `template`, `use`, `slot`, and the version="2" tags) are in the closed vocabulary, which `tuimark catalog` prints, and are not "inventing tags".

### Attributes per tag

- `bind`: action, keys, to, when
- `box`: border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, style, title, width
- `button`: border, class, disabled, focusable, gap, height, hidden, id, if, label, on:click, on:focus, pad, style, title, width
- `col`: border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, style, title, width
- `input`: bind, border, class, disabled, focusable, gap, height, hidden, id, if, on:change, on:click, on:focus, on:submit, pad, placeholder, secret, style, title, width
- `item`: border, class, disabled, gap, height, hidden, id, if, pad, style, title, width
- `keymap`: (no attributes)
- `list`: bind, border, class, disabled, each, focusable, gap, height, hidden, id, if, key, on:click, on:focus, on:select, pad, style, title, width
- `modal`: bind, border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:close, on:escape, on:focus, on:open, open, pad, style, title, width
- `progress`: bind, border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, style, title, value, width
- `row`: border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, style, title, width
- `rule`: axis, border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, style, title, width
- `screen`: class, focus, id, style, title
- `scroll`: axis, border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, style, title, width
- `spacer`: border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, style, title, width
- `style`: src
- `text`: border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, style, title, width, wrap
- `tui`: theme, version

Inside a list `<item>` nothing takes focus (the list does and navigates its rows): no `input`, `button`, `list`, or `modal` (V001), and no `focusable`, `on:click`, or `on:focus` (V002) anywhere in the row. Handle a row with the list's `on:select`, or a keymap row such as `<bind keys="d" action="delete" when="#rows:focus"/>` for `<list id="rows">` (its event identifies the selected row).

Bindings contain no spaces: `{path}`, `if="path"`, `if="!path"`, and exactly one space on each side of `as` in `each="path as alias"`.

Only in a `<tui version="2">` document (V002 with `(requires version="2")` in a version="1" one): the additions to the tags above, and the full attribute sets of the new tags:

- `bind`: keycap, label
- `box`: each, key
- `col`: each, key
- `column`: class, id, on:click, style, title, width
- `hints`: border, class, disabled, focusable, gap, height, hidden, id, if, on:click, on:focus, pad, scope, style, title, width
- `list`: checked, mark, on:change
- `row`: each, key
- `sparkline`: bind, border, class, disabled, focusable, gap, height, hidden, id, if, max, min, on:click, on:focus, pad, style, title, width
- `tab`: border, class, disabled, focus, gap, hidden, id, if, label, pad, short, style, title
- `table`: bind, border, checked, class, disabled, each, focusable, gap, height, hidden, id, if, key, mark, on:change, on:click, on:focus, on:select, pad, placeholder, style, title, width
- `tabs`: bind, border, class, disabled, focusable, gap, height, hidden, id, if, mark, on:click, on:focus, on:select, pad, style, title, width
- `tui`: mouse
- `item` inside a `table`: class only (plus `class:NAME`)
- every tag except `tui`, `style`, `keymap`, `bind`, and the composition tags (`include`, `fragment`, `template`, `use`, `slot`): `class:NAME` (the name is open and lowercase, `[a-z_][a-z0-9_-]*`; the value is `path` or `!path`)

Only in a `<tui version="3">` document (V002 with `(requires version="3")` in a version="1" or version="2" one): these attributes on top of the tags above (a tag itself unknown in an older version still gets only its own V001, with the version="2" hint, so an attribute on it — `scale` on `sparkline`, `priority` on `column` — reports nothing further there):

- `column`: priority
- `keymap`: when
- `modal`: focus
- `scroll`: stick
- `sparkline`: scale

Only in a `<tui>` without `version` (V001 or V002 with ` (requires a <tui> without version)` in a document that writes `version`): these attributes on top of the tags above, and the full attribute sets of the new tags:

- `checkbox`: bind, border, class, disabled, focusable, gap, height, hidden, id, if, label, on:change, on:focus, pad, style, title, width
- `fragment`: (no attributes)
- `include`: src
- `list`: single
- `progress`: indeterminate
- `select`: bind, border, class, disabled, each, focusable, gap, height, hidden, id, if, key, label, on:change, on:focus, pad, placeholder, style, title, width
- `slot`: (no attributes)
- `table`: single
- `template`: id, props
- `use`: class, hidden, id, if, template, with

### Key tokens

Named: enter, esc, tab, backspace, space, up, down, left, right, home, end, pgup, pgdn, shift+tab

Also valid: `ctrl+<a-z>` (`ctrl+i`, `ctrl+j`, and `ctrl+m` arrive as `tab`/`enter` and never match: in a keymap of a `<tui>` without `version` each is V003, so write `tab` or `enter`; a document that writes `version` accepts them, never matching, as before; `play` steps accept them in every document and deliver `tab`/`enter`), and any single printable ASCII character except space (write `space`) and `,` (the `keys=` list separator; a token of `,` binds nothing).

### v0.2a: interaction, styles, and theme

- `tuimark play FILE --data sample.json --input "STEPS" --format json` replays keys, `text:`, `paste:`, `set:`, `focus:`, and `resize:` steps against the document without a TTY (or `--script FILE.ndjson` for steps that need embedded spaces or explicit JSON) and prints the final dump plus every action that fired (`events`), so an agent can check that typing into a search box, or moving a list selection, fires the right `on:` action before wiring a Go handler. `--frames` adds one settled frame per applied step. `tick:DUR` (`tick:250ms`, `tick:1.5s`, `tick:1m30s`; units `ms`, `s`, `m`, `h`; a whole number of milliseconds from 1ms to 1h) advances the virtual clock by DUR, which is what turns a `<progress indeterminate="true"/>` spinner (one glyph, phase `floor(V / 100ms)`; `dump` always paints phase 0) and fires a Go host's `Every` functions; it works against every document and `--script` writes it `{"tick":"250ms"}`.
- `tuimark dump FILE --styles --format json` (also `play --styles`) adds `theme` and per-row `styles` spans to the dump, so `:focus`, `:selected`, theme tokens, and a `reverse` selection are checked by diffing JSON instead of eyeballing `preview`.
- `--theme dark|light` on `dump`, `validate`, `preview`, `play`, and `inspect` overrides the document's `theme` for that render (`Run`'s equivalent is `TUIMARK_THEME`). `auto` and any other value the flag is explicitly given — including `""` — are usage errors (no tool probes the terminal); only leaving `--theme` off keeps the document's theme. A document's `theme="auto"` (version="2") is `dark` in every tool.
- `preview --color truecolor|256|16|none` picks the ANSI grid's color profile; without it, `preview` falls back to `TUIMARK_COLOR`, then to the same detection `Run()` uses (SPEC §26.3) — read only when stdout is a TTY, resolved once per `preview`.
- `Run()` also reads `TUIMARK_THEME` and `TUIMARK_SYNC` (forces synchronized-output framing off/`0`/on/`1`); `dump`, `validate`, `play`, `ir`, `fmt`, and `test` never read any `TUIMARK_*` variable, so their output never depends on the environment.
- `L006` (new in 0.2a) means a `scroll`/`list`/`overflow: scroll` viewport can never show part of its content: 0 cells on its scroll axis while it has content there, or clipped by an ancestor that does not itself scroll on that axis. Give it a size, or put it in a `<scroll>`.
- `"wide": true` on a dump means some row holds a cluster wider than one column or made of more than one code point (an emoji, CJK, a combining mark): index `cells`, not `grid` by rune, when it is set.
- `tuimark test --update` refuses to rewrite a non-frozen JSON golden that is not a superset of the one on disk (same fields, same values, nothing removed or changed; new members/nodes may only be added when arrays keep their length) and exits 2 naming the first differing JSON Pointer; `--allow-breaking` writes it anyway, for a reviewed, deliberate change.

### version="2" (0.2b)

- `<tui version="2">` opts a document into the 0.2b vocabulary; everything a version="1" document accepts keeps its meaning there. In a version="1" document each 0.2b tag is V001, each 0.2b attribute V002, and each 0.2b value, property, pseudo-class, media feature, or built-in action V003, with a message ending in `(requires version="2")`. A `.tcss` file has no version of its own: it is checked against the version of the document that loads it. Any `version` other than `1`, `2`, or `3` is V003, and the document is read as version="1" (`version="3"` is accepted too, see "version=\"3\"" below).
- Tags only version="2" accepts: table column tabs tab sparkline hints. This build lays out and paints all six (below).
- `class:NAME="path"` (or `!path`) adds the class NAME while the guard is truthy; a missing path is B002 and counts as null, as for `if` (`class:x="path"` adds nothing, `class:x="!path"` adds x). The JSON dump of a version="2" document lists each node's `classes` (its `class` names, then its truthy guards, each name once: `class="a b a"` gives `a b`); a version="1" dump never has `classes`. The names `tab-label`, `hint-key`, and `hint-label` are reserved for classes the runtime gives generated nodes.
- `theme="auto"`: `Run()` asks the terminal for its background (OSC 11, waiting at most 250 ms before the first frame), falls back to `COLORFGBG`, then to `dark`. Every command and `Dump()`/`Validate()` treat `auto` as `dark`; `validate` checks an `auto` document under both themes, dark first, and reports each diagnostic once.
- `@media (theme: dark)` and `@media (theme: light)` (version="2" stylesheets) hold per-theme rules and `:root` palettes. Tokens apply in document order, so put a `@media (theme: light) { :root { … } }` block after the base `:root` it refines. `@media (theme: auto)` is V003.
- `Set("@theme", "dark"|"light"|"auto")` (a reserved path, both versions) is the host's theme: it beats the document's theme and `--theme`, and `TUIMARK_THEME` beats it in `Run()`. `play` sets it with `set:@theme="light"` or the script step `{"theme":"light"}`.
- Properties only version="2" stylesheets accept: `grid-columns`, `grid-min-width`, `scrollbar`, `bar`, and the value `layout: grid`. This build applies all of them (below). Pseudo-classes (+10 each, like the others): `:focus-within` matches the focused node and each ancestor up to the screen, through a modal, and nothing while nothing is focused; `:checked` matches a list or table row whose key is in the widget's `checked` array.
- `<table id="t" each="rows as r" key="r.id" bind="cur">` holds `<column title="Name" width="1fr">{r.name}</column>` elements (the body is the cell template, resolved per row) and at most one attribute-only `<item class="…" class:NAME="…"/>` row template. It shows one row per array element; it is focusable and keeps a cursor like a list (it consumes `up`, `down`, `home`, `end`, `pgup`, `pgdn` while it has rows, paging by its body height; `bind` receives the cursor row's key with its JSON type; `on:select` fires with `keys` = `{alias: key}`), its scroll offset follows the cursor, and it lays out, paints, and dumps only the rows in its body viewport (`scroll.h` is the row count, the header excluded). The header row (the `column` nodes, whose dump `text` is the resolved `title`) is shown when a visible column has a `title` attribute. Column widths: `width` in cells; `%` of the width left after the mark channel; `fr` shares what is left, then `min-width`/`max-width` clamp it; unset or `auto` is the widest of the title and the cell texts over every row. Columns that do not fit are clipped (no horizontal scroll), and a column with `display: none` (say under `@media`) hides its header and its cells. Cells never wrap (`wrap: wrap` truncates). A rule on a `column` styles its header cell only; the body cells (`table > item > text`, no id) carry the column's `class` and its `class:NAME` guards evaluated on their row, so style them with a class or `#t > item > text`. The rows are `table > item` (the built-in sheet reverses the cursor row) and ignore their own sizes, borders, and spacing. `placeholder` is painted dim and centered on the first body row when the array is empty. `checked`/`mark` and the `move-*` and `check-*` built-ins work on a table as on a list. A table needs `id` (V012), `each` and a `column` (V017), and without `key` reports B006; misplaced children are V016.
- `<tabs id="nav" bind="view" mark="▸" gap="2" on:select="changed">` holds `<tab id="overview" label="1 overview" short="1 ovr" focus="#x">…</tab>` elements: a one-row strip of labels, and below it the content of the active tab only (inactive tabs are not inflated or laid out; their widgets keep their state by id). With `bind`, the active tab is the visible tab whose id is the bound string (`null` or a missing path, B003, give the first visible tab; any other value too, with B010; fallbacks never write the store); without `bind` the runtime remembers it. `switch-to` a tab, `move-next`/`move-prev` (wrapping over the enabled tabs)/`move-first`/`move-last` on the tabs, `left`/`right` on a focused tabs (`focusable="true"` in a document that writes `version`; a `tabs` of a `<tui>` without `version` is focusable by itself), and `action="focus"` into an inactive tab (not a nested tab already active by a fallback) activate a tab: they write its id to `bind` (or remember it) and fire `on:select` with `value` = the id; a host `Set` activates without `on:select`. Labels are generated `text` nodes (class `tab-label`, `key` = the tab id, `:selected` for the active tab, `:disabled` for a disabled one, which the keys skip); they show every `label` when they fit, else every `short` (an empty `short` counts as absent), else only the active tab's as `‹ label ›` (then `‹ short ›`, then truncated), each after a mark slot of `width(mark)` columns, `gap` apart; their own sizes, spacing, borders, and `display` are ignored. When the active tab changes and focus was on the strip (in a document that writes `version`; in a `<tui>` without `version` focus on the strip stays there), inside the old tab, or nowhere, focus moves to the new tab's `focus=`, else its first focusable node, else the screen's rule (`on:select` first, then that node's `on:focus`); when one frame changes several tabs while focus is nowhere, only the first in document order moves it; on a screen's first frame the first tabs whose active tab has a focusable `focus=` supplies the focus when `screen@focus` does not. `tabs` and `tab` need an `id` (V012), a tabs a `tab` (V017) and only tabs (V016), a tab a non-empty `label` (V003), and `tab focus=` a node inside it (B005).
- `<sparkline bind="hist" min="0" max="100"/>` draws the last values of a numeric array as bars, one column per value, eight levels per row, right-aligned (`null` is a gap; without `min`/`max` the shown values give the range; a flat series is half high). It is as wide as the array and one row high by default. A non-array or a non-number element is B009; a missing path B003.
- `<hints/>` shows the keymap rows with a `label` (their `keycap` when it is not empty, else the key, then the label): `scope="active"` (the default) only those one of whose keys would fire now through the key dispatch (a key the focused input takes, a row shadowed by an earlier row with the same key, an `esc` row under a modal with `on:escape`, a built-in whose target does not match: hidden), `scope="all"` every one. Items are laid out along the row (or down with `layout: column`), `gap` apart (`hints { gap: 2 }`), and the first that does not fit is dropped with every item after it. Each item is a generated `row` (`hints > row`, gap 1) with a `.hint-key` and a `.hint-label` text.
- `layout: grid` on `screen`, `box`, `col`, `row`, `scroll`, `item`, `tab`, or `modal` places the in-flow children in equal columns, row by row: `grid-columns: K` columns, or, with `grid-min-width: M`, `clamp(floor((W + gap) / (M + gap)), 1, K)` for the content width W the docked children leave (they are pulled out first, in a `scroll` too, where they scroll with its content), so no `@media` is needed; without `grid-min-width`, an auto-width grid is as wide as K columns of its widest child. `gap` separates columns and rows; a row is as tall as its tallest child; `align` places shorter ones. A child's `width`, `min-width`, `max-width`, `flex`, and `fr`/`%` `height` are ignored (L007 when the document wrote them). A grid box never shrinks; a `<scroll>` (or `overflow: scroll`) grid fits the space left and scrolls its rows.
- `scrollbar: auto` on a viewport (a `scroll`, `list`, `table`, or `overflow: scroll` box) that scrolls on y, has a border, is at least 3 rows tall, and has more content than fits paints a thumb over its right border (`┃`, or `█` on `double` and `thick` borders), sized and placed by the offset; it never takes layout space. `scrollbar: none` is the default.
- `bar: eighths` on a `progress` fills in eighths of a cell (`▏▎▍▌▋▊▉` for the partial one) instead of whole cells (`bar: block`, the default).
- `each="path as alias"` (and an optional `key="path"`) also goes on `col`, `row`, and `box`: every child element is the template, inflated once per array element, in order, with the alias in scope (`{path}`, `if`, `hidden`, `disabled`, `class:NAME`, and a `progress` `bind` resolve per element). The container's own `if`, `hidden`, `disabled`, `title`, and guards use the enclosing scope, and it is not repeated. Each generated top-level node dumps the element's `key` (the index without `key=`). A missing or non-array path is B001; an empty array leaves the container empty (`:empty`). The template holds nothing that takes focus or keeps state: `input`, `button`, `list`, `modal`, `table`, `tabs`, `tab` are V001, `focusable`/`on:click`/`on:focus` V002, and any `id` V004. An alias equal to an enclosing one is V011.
- Multi-select: `checked="path"` on a `list` or a `table` (with `each` and `key`, else V018) holds the keys of the checked rows, an array the runtime reads and writes (a missing path counts as `[]`, B003; a non-array is B008, shown as nothing checked and never overwritten, and the `check-*` rows skip that widget; so does a missing path under a value that is not an object, such as `sel.marked` with `sel` a number, which the runtime could not write). A list's rows are the elements of its array even when `if`/`hidden` removes their item: the cursor can rest on such a row and `check-toggle`/`check-all` include it, so filter the array in the host rather than hide items. `mark="✓"` (1 or 2 columns, needs `checked`: V018) reserves `width(mark) + 1` columns at the left of every row and paints the mark on checked rows. `on:change` on a `list` (needs `checked`: V018) fires with `value` = the new array when `check-toggle`, `check-all`, or `check-none` changed it. Checked rows dump `"checked": true` and end their text node line with ` checked`. Bind the keys yourself (`space`, `ctrl+a`, … are not implicit).
- Keymap rows of a version="2" document take `label` and `keycap` (literal text, carried in `tuimark ir`; a row with a `label` is a key hint that `<hints>` shows) and the hyphenated built-in actions (move-next, move-prev, move-first, move-last, move-page-down, move-page-up, check-toggle, check-all, check-none, switch-to), which are built in (never B004; `Catalog()` lists them with `builtin: true`) and allowed only in keymap rows (in `on:*` they are V003). A built-in acts on the node named by `to=`, else on the focused node: `move-next`/`move-prev`/`move-first`/`move-last`/`move-page-down`/`move-page-up` move a list's or a table's cursor (writing `bind`, firing `on:select` when it moved), a viewport's offset, or a tabs' active tab (not `move-page-*`); `check-toggle`/`check-all`/`check-none` change a list's or a table's `checked` array; `switch-to` (needs `to=`, V003 otherwise) activates a visible, enabled tab whose tabs is in the frame, or switches to a screen. A row whose target is missing from the frame, disabled, or incompatible (an empty list or table, one without `checked`, a button, …) does not match, and the key goes on to the next rows; a matching row takes its key even when nothing changes (`move-next` on the last row). B007 (an error, reported without data) names a target known to be incompatible from `to=` or from a `when` that is exactly `#id:focus`. `play` records the events they fire, not the actions.
- `when` in a version="2" keymap matches over the focus chain: the focused node and each ancestor up to the screen (a modal's parent is its screen), or, with nothing focused, the top open modal and then the screen. So `when="#pane"` holds while focus is anywhere inside `#pane`, and `when="#kill"` while it is inside the modal `kill`. A host action fired by such a row still names the focused node as its `source`. In a version="1" document `when` matches the focused node only, and nothing while nothing is focused.
- One key dispatch serves `Run()`, `play`, and `<hints>`: (1) `esc` fires the top modal's `on:escape`, or, in a `<tui>` without `version`, closes a modal that has none (see the defaults of the current language); (2) a focused, enabled widget consumes its keys (an input: printable keys, `space`, `backspace`, `ctrl+h`, `ctrl+u`, `left`, `right`, `home`, `end`, `ctrl+a`, `ctrl+e`, and `enter` with `on:submit`; a list or a table with rows: `up`, `down`, `home`, `end`, `pgup`, `pgdn`; a focusable tabs with an enabled tab: `left`, `right`; another viewport: the arrows, `pgup`, `pgdn`, `home`, `end`; any other node with `on:click`, except a list or a table: `enter` and `space`); (3) the first keymap row, in document order, whose keys, `when`, and built-in target match (while a modal is open in a `<tui>` without `version`, only a row whose `when` matches inside it: see the defaults of the current language); (4) `tab`/`shift+tab` cycle focus and `ctrl+c` quits.
- `<tui version="2" mouse="path">` turns the mouse on while its flag (`true`, `false`, a path, or `!path`; the default is `false`; a missing path is B002 and counts as null, so `mouse="path"` is off and `mouse="!path"` is on) is truthy; it is evaluated on every frame, so a host (or a Settings screen) switches it with `Set`, and `Run()` turns the terminal's mouse reporting (SGR) on and off with it. Only the left button and the wheel act, against the frame on the screen; while a modal is open only events inside the top modal count, and there only the modal and its nodes receive them, even when it paints nothing (`visibility: hidden`). A click acts on release over the same node (for a list or table row, the same row by its index and key: when the table scrolls or the host reorders the array between press and release, so that another row lies under the pointer, nothing happens): walking up from the node under the pointer, a disabled or `visibility: hidden` node stops it; a tab label activates its tab; a row of a list or a table focuses the widget (`on:focus`) and moves the cursor there (`on:select`); a `column` with `on:click` fires it without moving focus; a node with `on:click` takes focus if it can, then fires it; any other focusable node takes focus. The wheel moves a list's or a table's cursor by one (`on:select`, focus stays), a tab strip by one tab (with wrap), or a viewport by one row (one without an `id` too). `play` replays the mouse with `click:X,Y`, `wheel-up:X,Y`, and `wheel-down:X,Y` (cells 0-based as in the dump; a cell outside the grid is a usage error; with the mouse off the step does nothing) or the script steps `{"click":[X,Y]}` and `{"wheel":"down","at":[X,Y]}`; `tuimark inspect --at X,Y` names the same node a click there starts from.
- `tuimark inspect FILE --at X,Y --json` (or `--id ID`) answers "why does this cell look like this?": the node that cell belongs to, its layout path, its pseudo-classes, every class it could have (with guards, and whether any rule names it), and every property with the rule that won and the rules that lost. It renders exactly as `dump` does with the same flags.
- `tuimark ir` prints `"version": "0.2"` for a version="2" document (validated by `schema/ir.v0.2.json`): the new kinds, `app.mouse`, the keymap's `label`/`keycap`, and `class:NAME` attributes under their full names in `attrs`.
- `TUIMARK_LOG=FILE` makes `Run()` write an NDJSON log of the session (a regular file is created or truncated with mode 0600; `/dev/null` or a pipe is written as it is; a terminal is refused): start, capabilities and the resolved theme, keys, pastes, mouse events and mouse mode changes, actions, frames, resizes, end. While a `secret` input has focus, key and paste records are redacted, and that input's events never carry their value. Only `Run()` reads it.

### version="3" (0.3a)

- `<tui version="3">` accepts everything a `version="2"` document does, with the same meaning (every version="2" rule above holds for it too, `when` over the focus chain and the dump's `classes`/`checked` included); a `.tcss` it loads is checked as for version="2". 0.3a gives it no vocabulary of its own: only the layout warnings `L008`/`L009` and the dump's `clipped` are new, and only for a version="3" document. A version="2" document is a valid version="3" document, so upgrading is one attribute, or none: a `<tui>` without `version`, the current language, holds every version="3" rule.
- `L008` (warning) is a painted `text` that loses content without saying so: (a) its computed `wrap` is `nowrap` (the initial value, or the literal `nowrap`), that value is not document-written, and its widest line is wider than its content box, so columns are cut with no ellipsis; (b) its lines after wrapping and truncation outnumber its content box's rows, and `overflow: hidden` is not document-written on it. Silence (a) by writing `wrap: nowrap` (an author's own choice, not the default) or `wrap: truncate`; silence (b) by writing `overflow: hidden` or giving it more room. It never fires on a table cell, a tab label, or a hint item (each has its own cut rule already), or on `visibility: hidden` text.
- `L009` (warning) is a container that cuts a child, in flow or docked, on an axis it does not itself scroll (a `<scroll axis="y">` is still checked on `x`): part or all of the child's outer rect falls outside the container's content box there. It is silenced by writing `overflow: hidden` on the container, and it is never reported for a `list`, a `table`, or a `hints` (they show part of their content by design), for a node `L003` already reported this frame (that message already explains the cut), or for a child `L006` already reported this frame (its own warning explains it); a child with `visibility: hidden` or an empty rect does not count.
- "Document-written" (both codes) means a presentational attribute, a stylesheet rule, or `style=""`, on the node itself or — `wrap` is inherited — on an ancestor it inherits it from; the initial value and the built-in sheet's own `table { wrap: truncate; }` never count. Each is reported once per source element and frame (a template's repeated rows collapse into one diagnostic), while the dump's `clipped` (`"text"` for `L008`, `"children"` for `L009`) marks every node that meets the condition, generated rows included.
- `tuimark ir` prints `"version": "0.3"` for a version="3" document, validated by `schema/ir.v0.3.json` (the same shape as IR 0.2 in 0.3a).

### version="3" (0.3b)

- Every 0.3b item below is `version="3"` only, except several `<keymap>` elements: in a version="1" or version="2" document it is the code listed in "Diagnostic codes" with a message ending in `(requires version="3")`; on a 0.2b tag in a version="1" document (`scale`, `priority`, a tab-label `{path}`) only that tag's `V001` is reported.
- `row-gap` and `column-gap` (0-4, initial 0) set the two gaps apart: `column-gap` between siblings side by side (a `layout: row` container's children, grid and table columns, the tab labels, a `hints` laid out along a row), `row-gap` between siblings stacked (a `layout: column` container's children, grid rows, a `hints` with `layout: column`). `gap: N` stays their shorthand in the cascade: it counts as both, with its own origin, specificity, and order, so `.x { row-gap: 0 }` loses to `#g { gap: 2 }`, and `#g { gap: 2; row-gap: 0 }` makes the rows touch. A document that sets only `gap` lays out as before. `inspect` lists both after `gap` in a version="3" document, the winner possibly a `gap` declaration.
- `wrap: truncate-start` keeps the end of each line (`…efgh`) and `wrap: truncate-middle` both ends (`/Syste…/Data` at 12 columns: the head gets the extra column). Like `truncate`, they never report `L008`, and a cut wide cluster is left out, so the result may be narrower (by up to two columns for `truncate-middle`). A table cell, header or body, follows its `wrap` among the three truncations; `wrap: wrap` is painted as `truncate` and `nowrap` is clipped with no ellipsis.
- `<column priority="N">` (a non-negative integer, else `V003`) lets a column hide when the table is too narrow: while the visible columns' natural widths (a cell width, `floor(A*p/100)` for `p%`, an `auto` column's clamped measure, an `fr` column's `min-width`) plus the column gaps exceed the width left, the column with the smallest `N` hides (the last in document order among equal `N`). A hidden column is exactly a `display: none` one (no header cell, no body cells, nothing dumped), but still counts in the table's intrinsic width and in whether the header row shows. It is re-evaluated every frame, so it comes back when the table widens; columns without `priority` never hide this way. Prefer it to `@media` rules for column hiding.
- `<sparkline scale="NAME">` (an identifier, else `V003`) shares a range: the laid-out sparklines of one frame with the same `scale` take `lo`/`hi` from the smallest and largest of all their shown values, while a member's own `min`/`max` literal still wins for that member. An inactive tab's sparkline is not in the group; a `visibility: hidden` one is. A group of one is the same as no `scale`.
- Several `<keymap>` elements are allowed, in every version: their rows form one keymap, in document order (the first keymap's rows, then the second's, and so on). `<hints>` and the top-level `keymap` array of `tuimark ir` see that single ordered list.
- `<keymap when="SEL">` (version="3") gives every row inside it that `when`, unless the row writes its own (which replaces it outright, never combines with it); `when=""` written on a row gives it no `when` even under a `<keymap when>`, and `when=""` on the `<keymap>` itself gives its rows no `when`. The `<keymap>`'s own `when` is checked once, at the `<keymap>` element (one `V003` for a bad selector, one `B005` for an id that names no node or a node inside a list item or an each template), not again for each row that inherits it; `B007` still checks each row against its effective `when`. `tuimark ir`'s top-level `keymap` array carries each row's effective `when`; the root tree keeps the `keymap` node and every `bind` node with their own `when` in `attrs`, as written. `Catalog()` shows no `when` at all.
- `<scroll id="log" stick="bottom">` keeps showing the end of its content as it grows, like a log or a chat: it needs an `id` (`V012`) and a `y` scroll axis (`V003` on `axis="x"`), and is `V002` inside a list `<item>` or a container `each` template (its state needs an identity across frames a repeated row does not have). The rule compares the offset a frame brings in (`o`, the last live frame's offset, as the wheel, `move-*`, or a focused scroll's keys have moved it since) with the previous live frame's maximum (`M'`, `EXTENT - viewport`, 0 when the content fit, or none yet for the first live frame): when `o >= M'`, this frame's offset becomes its own maximum, so it keeps sticking; otherwise the offset stays at `o`, so scrolling up and reading back while the content grows does not jump. `move-last` (or the wheel/keys down to the end) makes it stick again from the next growth on. `tuimark dump`, `validate`, `Validate()`, the first frame of `play`, and `Dump()` on an app with no live frame yet show the end, as a first live frame does; `Dump()` on a live app applies the rule with the live `o`/`M'` at its own size and changes neither.
- In a `<tui version="3">` document a `tab`'s `label` and `short` are templates, exactly like a `<text>` body (`{path}`, no expressions): resolved every frame against the store (a `tabs` is never inside an each template or a list item, so no alias is ever in scope), a missing path is `B003` and resolves to the empty string, and each LF a resolved value brings becomes a space, since a label is one row. `short`'s emptiness (whether it falls back to the resolved `label`) is judged after resolving, so a counter that resolves to nothing falls back exactly as an absent `short` does; the label tier (`W1`/`W2`, SPEC §6.10.4) is computed from the resolved widths, so a counter that grows can move the strip from tier 1 to tier 2 in the frame where it grows. `label` is still judged non-empty as *written* for `V003` (an empty resolved string still counts as present, painting `m` columns for the mark alone). In a `version="1"` or `version="2"` document `{path}` in a tab's `label`/`short` stays `V003`, now with the `(requires version="3")` hint; `mark` stays literal text in every version.
- `<modal id="m" focus="#id">` names the node that takes focus when the modal becomes the top one, instead of the first entry of its focus cycle: the target must be inside the modal (`B005` otherwise, mirroring a `tab`'s `focus=`). It is also the fallback when the node focused inside the top modal is lost (leaves the frame, or can no longer take focus): focus goes to it when it can take focus, else to the first entry of the cycle, and that node fires `on:focus`. When the target cannot take focus this frame (not laid out, hidden, disabled, not focusable), the first entry of the cycle is used, as without the attribute; focus already inside the modal never moves. While a modal is open the screen's `focus=` is never the lost-focus fallback, `focus=` or not; on a screen's first frame it still sets the initial focus first, so a target inside the open modal keeps it there.
- `tuimark host FILE [--data FILE.json] [--theme dark|light] [--reply-timeout 5s]` runs a document in the terminal for a parent program in any language (POSIX only; on Windows it is a usage error): the terminal stays on fd 0/1/2 exactly as with `Run()`, the parent writes JSON lines to fd 3 (`set`, `bind`, `batch`, `get`, and `reply`) and reads JSON lines from fd 4 (`ready` first, with `protocol` 1, the size, theme, catalog, and diagnostics; then `event` with a `seq`, `ack`, `error`, and `exit` last). Each `event` waits for the parent's `reply` (`quit`, `error`) up to the reply timeout; the fd 4 queue is bounded, so a parent that stops reading ends the session instead of freezing the terminal. `examples/host-ts` is a Bun parent: it passes `stdio: ["inherit", "inherit", "inherit", "pipe", "pipe"]`, forwards SIGTERM/SIGHUP to the child, and never reads the terminal itself.
- `tuimark mcp` is a Model Context Protocol server on stdin/stdout (stdlib JSON-RPC, one message per line) whose tools run the Loop: `tuimark_validate`, `tuimark_dump`, `tuimark_play` (its `steps` is an array, one step per element, so a step may hold spaces), `tuimark_inspect`, and `tuimark_agents` (this briefing). Each returns exactly what the matching command prints; a result is `isError` only when the command would exit 1 (validation errors, exit 2, are a normal result).
- The Go API: `Batch` returns every failed part joined (`errors.Join`, so `errors.Is` still finds a sentinel, but `==` no longer does), and `PlayOptions.Frames` makes `Play` return one `PlayFrame` per applied step in `PlayResult.Frames`, as `play --frames` prints them.

### v0.4a: tools and the Go API

- `tuimark catalog` prints the closed vocabulary as one JSON object, so an editor or an agent reads it instead of scraping this file. It takes no flags and reads no environment variable. Members: `catalog` (the format version, 1), `tuimark` (the bare runtime version), `versions` (the document versions this build accepts), `tags` (each with its `attrs`, and an enumerated attribute's `keywords`), `properties` (each with its `syntax` and `keywords`), `pseudo_classes`, `media` (each with `keywords`), `keys`, `actions` (`builtin`, `needs_to`, and `keymap_only`, true for the hyphenated built-ins that only keymap rows may name), and `diagnostics` (the codes of the table above). On every item, `since` is the lowest document version that accepts it, so an attribute a tag gained later carries its own (`checked` on `list` is 2). An item that takes only numbers, sizes, colors, paths, or text has `keywords: []`. The catalog lists what each tag accepts anywhere: contextual rules, such as what a list `<item>` may hold, are the diagnostics' job. Removing or renaming a member needs `catalog: 2`; adding members, items, or versions does not.
- `tuimark new NAME [--go | --ts]` creates a project in the directory `NAME`, which must not exist or must be empty (otherwise it is a usage error that writes nothing, and no file is overwritten): `app.tui` (with no `version`, so the current language, with a bound list, a status line, a keymap with labeled rows, and `<hints/>`), `theme.tcss`, `sample.json`, and this briefing as `AGENTS.md`. `--go` adds `main.go` and `go.mod`; `--ts` adds `parent.ts` and `package.json` (a Bun parent through `@thelacanians/tuimark`). The two flags are exclusive. `new` prints the files it wrote, then the next command.
- `tuimark run FILE [--data FILE.json] [--theme dark|light] [--events FILE.ndjson] [--mock FILE.json] [--strip]` shows the document live in the terminal with no host program, for a person to try it: the session is `Run()`'s, `--data` is bound at the root, and `--theme` is applied as `Set("@theme", …)`. Every non-builtin action is answered by `run` itself: its `--mock` writes (one JSON object, `{"ACTION": [{"path": P, "value": V}, …]}`, literal values) are applied as one `Batch`, then the event is recorded in the event strip and in `--events` (one `{"seq","action","source","keys","value"}` line per action, mode 0600; a `secret` input's event has no `value` and ends with `"redacted": true`). `F12`, or `--strip` from the start, shows the strip over the bottom rows: `ACTION SOURCE KEYS VALUE` as `play` prints an event, `! ACTION: ERROR` for a failed mock batch, `reload`. A panel over the top rows lists the static diagnostics, or a failed reload's error. Saving the document, a stylesheet it loads, `--data`, or `--mock` reloads it in place, keeping the store (unless `--data` changed) and, by id and tag, the focus, the screen, cursors, scroll offsets, input text, and the active tab; a failed reload keeps the old document running. `quit` and an unbound `ctrl+c` exit 0, and two `ctrl+c` within a second always do. A bad `--mock` (an unknown or built-in action) or an `--events` path that is a terminal is one `tuimark: run: …` line and exit 1, before the terminal is touched. To check a document, use `play`: `run` is for a person at the keyboard.
- `tuimark agents --project` prints this briefing as `new` writes it into a project, so it can be regenerated after an upgrade; `tuimark agents` without a flag prints it for the authoring task as before. `--repo` and `--project` are exclusive.
- `tuimark validate` without `--data` ends its text output with `ok (bindings not checked: no --data)` instead of `ok`, since `B001`-`B003` and `B008`-`B012` were not checked; with `--data` the line stays `ok`, and warnings are still printed before it. `validate --json` has the members `actions`, `data`, `diagnostics`, `file`, and `ok`, where `data` is the `--data` argument as given, or `null` without it (so an agent reads from it whether bindings were checked, and against which file). `tuimark_validate` returns this JSON.
- `tuimark lsp` is a Language Server Protocol server on stdin/stdout for `.tui` and `.tcss` files, which an editor starts (the VS Code extension does). Its diagnostics are the ones `tuimark validate` prints, with a `sample.json` beside the document used as if passed with `--data`, and it offers completion, hover, definition, and `.tui` formatting from the catalog. It takes no arguments and reads no environment variable.
- A Go host (`main.go`) has five more methods; a document never names them. `RunContext(ctx, w)` and `RunWith(ctx, w, RunOptions{OnError})` run the app under a context (a cancellation ends the session as a quit and restores the terminal) and with an error policy (`OnError` gets each error a handler, an `Every`, or a `Derive` returns: `nil` goes on, `ErrQuit` quits, any other error ends `Run`). `Quit()` ends the session from any goroutine. `Every(d, fn)` calls `fn(*Batch)` every `d` on the loop, its writes applied as one `Batch` with one redraw; `Dump` and `Validate` never call it, and `play` advances its virtual clock only on `tick:DUR` steps (see the `play` bullet of the v0.2a section), so a `play` without them never does either: check time-based state with `tick:` and `set:` steps. `Derive(path, fn)` keeps a computed value (a filtered list, a count) at `path`, recomputed inside every store write, so the markup reads it like any other path and stays free of expressions: write `<list each="visible as r">` over a `Derive` of `visible`, not an expression in the document. A derived path is read-only: `Set` on it is an error, and a widget bound to it does not change.
- A line of 64 MiB or more (the newline excluded) on `tuimark host`'s fd 3, or on `tuimark mcp`'s stdin, ends the session: `host` writes `{"type":"error","error":"fd 3 line of 64 MiB or more"}` on fd 4 and ends with reason `error`, applying nothing of the line; `mcp` exits 1.

### v0.4b: composition

- `<include src="FILE"/>`, in a `<tui>` without `version`, places the elements of another file where it stands: directly under `<tui>`, in a `<screen>`, in a container, or in a `<keymap>`. `src` is relative to the file that writes the include (a fragment's, to the fragment). The file's root is `<fragment>`, which takes no attributes (`V002`) and is `V001` anywhere but the root of an included file; it may hold several elements and other includes. Ids, styles, and data are shared, and the document is checked as if the elements were written where the include stands; a diagnostic about an element an include placed ends with `, placed by <include> at FILE:LINE:COL`. A cycle, a file outside the file system a `LoadFS` host gave the document, or one that cannot be read is `V006` at the include; a stylesheet, or a file whose root is not `<fragment>`, is `V020`; an include that fails inserts nothing and the rest of the document is still checked. A fragment is not a document: `dump`, `play`, `preview`, `ir`, and `inspect` give it `V005` ("check it through the document that includes it") and exit 2, while `validate` and `fmt` accept it.
- `<template id="T">` holds a piece of markup that is never drawn by itself, and `<use template="T" with="path as alias"/>` is replaced, when the document is read, by a copy of it built where the use stands. A template is a direct child of `<tui>` or `<screen>`, in the document or in a fragment (elsewhere is `V001`), may come after its uses, and needs an `id` (`V012`; a second one with the same id is `V004`). Its body is one or more elements, never `tui`, `app`, `fragment`, `screen`, `style`, `keymap`, `bind`, or `template` (`V001`), and no loose text (`V013`). A `<use>` is not a node: it takes `template`, `id`, `with`, `if`, `hidden`, and a static `class` (any other attribute is `V002`, except a prop its template declares) and, as content, only the markup its template's `<slot/>` receives (`V013` when the template has none); one without `template`, naming no template, or closing a cycle of templates is `V019`.
- Ids in a copy are scoped by its use: `<use id="billing">` makes the `x` of the template `billing__x`, and a use inside a template scopes by both (`billing__street__input`). Outside the copy (`to=`, `when=`, `focus=`, `#id` selectors, `focus:` steps, an event's `source`) write the scoped id; inside the template a `#x` means the element of the same copy. A use without an `id` whose template holds an `id` at any depth is `V012`; a `to=`, `when=`, or `focus=` that names a use, or an id that only a template writes, is `B005` with the scoped id in the message; the id of a use is an id of the document (`V004` when repeated), and the copies of different uses never clash.
- `with="path as alias"` (several clauses separated by exactly `, `) makes the alias stand for the path inside the copy: `{f.label}` reads `form.email.label` and `bind="f.value"` reads and writes `form.email.value`; nothing is copied, and an input in a copy creates a missing path when it writes. A copy also reads the aliases in scope where its use stands (a list row's `each` alias), and a `with` path may start with one; an inner `each` alias that repeats such an alias shadows it inside the copy, while one that repeats a `with` alias is `V011` at that element (the copy is still placed). A malformed `with`, an alias written twice, or one already in scope at the use is `V011` and the use inserts nothing.
- `if` and `hidden` on a use are read where the use stands (its own `with` is not in scope) and decide whether its copy exists; in a list `<item>`, an `each` container, or a table they are decided per row, and a missing path is one `B002` at the use. A static `class` on a use is appended to every top-level element of the copy, after the classes the template wrote and before its `class:NAME` guards. A `<column>` cannot hold a `<use>` (`V016`): to reuse a column or the row `<item>`, make it the template and put the `<use>` directly in the `<table>`; its `if`/`hidden` stay per table, and a `with` path that starts with the row alias is read for every row.
- The expansions of includes and uses share a budget: more than 100000 elements, 16 MiB of placed source, or 256 levels of nesting is `V021` at the include or use that went over, which inserts nothing and stops every later one; a fragment an `<include>` places inside a `<template>` has a budget of its own ("exceeds the expansion limit for template definitions"). `V019` names a simple cycle through the use, starting at its own template: up to 8 templates whole, else the first 8, `… (N more)`, and the template it returns to. A `with` path that is missing is one `B003` at the use (`with path "form.phone" (alias f) is missing`) and nothing more from the copy; `if`, `hidden`, `disabled`, `open`, and `class:NAME` read through an alias that stands for an object are null when the member is missing, without `B002`, while a `{path}` or a `bind` is `B003`.
- A diagnostic about a path that went through an alias ends with `(P via <use id="U">)`, where P is the path the alias stands for; a use without an `id` is named `<use template="T">`, and ` at FILE:LINE:COL` follows when P starts with an `each` alias. Any other diagnostic about an element of a copy ends with `, placed by <use …> at FILE:LINE:COL`, and the location is the template's own line. An id, a path, or a template name a message quotes is cut at 64 bytes (at a character boundary) and followed by `…`.
- The tools show the expansion. `tuimark inspect` ends with `source FILE:LINE:COL`, the element the node was built from, then one `via` line for each use, include, or slot that placed it, nearest first (`--json`: a `source` member `{file, line, col, via}` whose entries are `{use, template, file, line, col}`, `{include, file, line, col}`, or `{slot, template, file, line, col}`; a node the document wrote itself has `"via": []`, and a document that writes `version` has no `source`). A slot entry, `via <slot/> of <use id="U" template="T"> FILE:LINE:COL`, names the `<slot/>` whose fill holds the node, and the use whose copy holds that slot appears only there, never as a use entry. `tuimark ir` keeps the composition as written: an `include` or `use` node holds the nodes it placed, in the template's own words (`f.value`, `{f.label}`) with scoped ids and every `{$name}` substituted, a copy's `slot` node (`attrs` `{"template": "T"}`) holds the fill it received, and each node they hold has a `from` member, `FILE:LINE`; a `template` node keeps its `props` and its body as written, a `<use>` there with its content and a `<slot/>` as a `slot` node. `fmt` substitutes no prop and fills no slot: a `<use>` with content is formatted as a container, one whose content is only whitespace is self-closing, and `<slot/>` is a self-closing leaf.`tuimark validate` of a fragment checks only its own elements, reads no file its includes name, and prints `ok (fragment checked on its own)` (JSON: `"ok": true`) with or without `--data`; `fmt` formats a fragment as a document with `<fragment>` as the root; `run` and `preview --watch` watch every fragment the last load read, at any depth, including one that does not exist yet; `tuimark_inspect` of a fragment returns the `V005` text as its result, not as an error. `tuimark lsp` gives a fragment the diagnostics the documents that include it give its file (found among the open documents and the `.tui` files of its directory and its parent), checks one no document reads on its own, follows `<include src>`, `template=`, and scoped ids across files for definition, and completes template ids and scoped ids; it also completes a `<use>`'s props (those its template declares and the use does not write yet) and, after `{$` in a template's body, that template's props, offers `slot` as a tag only in a template's body or in a fragment, and resolves a `{$name}` or a prop attribute of a `<use>` to the name in the template's `props`.
- Conventions for a reusable piece (a template and its uses):
  - Name an id of a copy by its scoped id, `#U__x`, in selectors, `focus=`, `to=`, and `when`, and never `#U`: the use is not a node (`B005`, with the scoped id in the message).
  - Pass data as a path: `with="form.email as f"` makes `f` the path, not a value, so the template reads and writes `f.value` in place and a diagnostic names the real path. What a copy needs to vary is a member of that object.
  - Vary one copy with a static `class` on its `<use>` (`class="wide"`): every top-level element of the copy gets it, and the stylesheet styles `.wide`. A use takes no `class:NAME` guard.
  - Pass a flag as an optional member of the `with` object (`f.required`, `f.error`): when the member is missing, `if`, `hidden`, `disabled`, `open`, and `class:NAME` read it as null with no diagnostic, so a copy whose object omits it has the flag off. A `{path}` or a `bind` on a missing member is `B003`.
  - Write the size of every template root (`<row style="height: 1">`): a `col` or `row` root is `1fr` only directly under a `screen`, a `modal`, or a `tab`, and content-sized anywhere else, so the same template takes different sizes in different places (see the defaults of the current language).
  - Read a diagnostic in a copy by its end: `, placed by <use …> at FILE:LINE:COL` names the use, and the location before it is the template's own line.
- The rest of the current language: its layout and key defaults are in the next section; the form controls and `{path}` in a `<button>` are in Notes; the spinner and `play`'s `tick:DUR` step, which advances it, are in the v0.2a `play` bullet.

### v0.4b: the defaults of the current language

A `<tui>` without `version` lays out and handles keys with the defaults below. A document that writes `version="1"`, `"2"`, or `"3"` keeps the 0.4.1 behavior each item names, and writing `version="3"` on a document keeps all of it; to see what a document owes to these defaults, run `dump --format json` at 80 and 120 columns on it and on a copy that writes `version="3"`, and diff the two. `tuimark inspect` shows the built-in rules as `ua`. Each item names its fix.

- **Content-sized `col` and `row`.** An unsized `col` or `row` is `1fr` × `1fr` only as a direct child of a `screen`, a `modal`, or a `tab` (the built-in sheet's `screen > col, screen > row, modal > col, modal > row, tab > col, tab > row { width: 1fr; height: 1fr; }`; a modal's parent is its screen, and the `col`/`row` children an `each` container generates are children of that container). Anywhere else it is `auto` on its parent's main axis and fills the cross axis, so a sidebar `col` beside a body `col` is as wide as its content and the body needs `width: 1fr` (or `flex: 1`), and a header or status `row` written directly in a `screen` is still `1fr` and needs `height: 1`. There is no `flex-shrink`: an `auto` pane never shrinks, panes wider than their row push the last ones out (`L009`, whose message names the fix), and a `wrap: wrap` text in an `auto` pane is measured unwrapped and does not wrap. A `%` child of such a `col` or `row` is `L002`; `justify` takes effect where `1fr` children used to fill the container, and a `spacer` in a container that is now `auto` on its axis has no leftover to take. A pinned document gives every `col` and `row` `1fr` and splits such a row between its `col`s in equal parts.
- **The sibling-fr rule, for viewports only.** An unsized sibling of an `fr` child stays `auto` and shares only what the `fr` children leave, except a viewport (`scroll`, `list`, `table`, or an `overflow: scroll` container), which becomes `1fr` on its parent's main axis. A sibling is `fr` when its main size is an `fr` size or a `flex` weight above 0, written or from the sheet (a `spacer`, and a `col`/`row` child of `screen`, `modal`, or `tab`); a viewport made `1fr` by the rule does not count, so two unsized lists side by side stay `auto`, and the split does not depend on the data (a list shares with an `fr` pane however many rows it has). So a `box`, `tabs`, or `hints` next to an `fr` pane takes its content size, a `list`, `scroll`, or `table` still shares with it, and a filter `row` above a list in a `screen`, `modal`, or `tab` is `1fr` and splits the space with the list: give the row `height: 1`. A `text` or a `button` is `auto` in every language. A pinned document also makes an unsized `box` next to an `fr` child `1fr`.
- **The `fr` freeze.** `fr` children share what the other children leave as CSS shares flexible lengths: a child whose share its `min-*` raises or its `max-*` lowers is frozen at that size, and the others share what is left again, round after round. Three `1fr` children in 40 columns with `max-width: 10` on the first are 10, 15, and 15, and with `min-width: 30` on the first they are 30, 5, and 5. A `min-*` larger than what is left keeps its size and overflows (`L003`). A pinned document splits first and clamps after: 10, 13, and 14 with 3 columns left empty, and 30, 13, and 14 with an `L009`.
- **Content-sized modals and hints.** A `modal` with no `width` (or `height`) is as big as its content on that axis, title, border, and padding included, capped by its `max-width` (`max-height`) and otherwise by 80% of the screen; a pinned document gives it 80% × 80%. Content over the cap is clipped at the modal's content box and reported as `L009` unless `overflow: hidden` is written on the modal, a `%` child on an axis where the modal is content-sized is `L002`, and a `col`/`row` child of the modal is `1fr`, so it takes what the other children leave (its content size when everything fits). The modal does not grow or move while the user types. A `hints` is as big as its items along their axis (`layout: row; gap: 2` in the sheet) and shrinks: the items that do not fit are dropped, with no diagnostic, and a container no longer reports `L009` for a `hints` it cuts. A pinned `hints` is an unsized `box` and shares its row with an `fr` sibling (20 of 40 columns next to a `spacer`).
- **`esc` closes a modal.** The top open modal that has no `on:escape` closes on `esc` by writing `false` at its `open` path (its `bind` path when it has no `open`), over whatever the path held; the next frame fires `on:close` and gives focus back, and no event fires for the key itself. A modal whose `open` is `true`, `false`, or `!path`, or whose path a `Derive` computes, stays open, because the runtime has nothing to write, and one with `on:escape` leaves the choice to that action: keep a modal open on purpose (a game-over screen) with one of these. A pinned document does nothing on `esc` without `on:escape`.
- **The modal trap and `<keymap when="modal">`.** While a modal is open, a keymap row fires only when it has an effective `when` that matches the chain from the focused node up to the top modal (`when="#dlg"` inside the modal `dlg`, `when="modal"` inside any modal); a row with no `when`, or whose `when` names something outside the modal, is not tried, so `q` cannot quit the app, and the arrows cannot move the board behind it, while a confirmation is open. `tab`, `shift+tab`, `ctrl+c`, and the keys the focused widget takes for itself still work (a `ctrl+c` row without `when` gives way to the built-in `quit`), and `<hints/>` shows only the rows that would fire, often none. A key that should also work under a modal is written again in `<keymap when="modal">`, a group whose rows all carry that `when` (a row's own `when` replaces it). A pinned document's rows fire under a modal.
- **`tabs` in the focus cycle, focus kept on the strip.** A `tabs` is focusable without `focusable="true"` (`focusable="false"` turns it off): `tab` and `shift+tab` reach it, `left` and `right` switch the tab, and focus on the strip stays on the strip when the active tab changes, where in a pinned document it moves into the new tab. A form's first `tab` may therefore land on the strip, a script that counts `tab` presses changes, and a `screen focus=` keeps the initial focus where the document wants it. A pinned `tabs` takes focus only with `focusable="true"`.
- **The built-in focus look.** The sheet ends with `button:focus, checkbox:focus, select:focus { reverse: true; }` (specificity 11), so a focused `button`, `checkbox`, or `select` is reversed over its whole rect with no author rule. An `input` gets none, since the terminal cursor shows its focus, and a focused `list`, `table`, or `tabs` keeps its own look (the cursor row, the active tab). An open option list is not reversed with its select (`select > list` has `reverse: false`). An author rule wins by origin: `button:focus { reverse: true; }` changes nothing, and another focus style adds `reverse: false` (`.k:focus { reverse: false; bold: true; }`). A pinned document has no such rule: it writes its own.
- **An `input`'s width.** An `input` with no `width` is `max(width(placeholder) + 1, 20)` columns whatever its value (a `secret` input's too), with the resolved placeholder, so typing never moves it, the nodes after it, or a modal sized by its content around it; write `width` (`1fr` fills the row) for another size. A pinned `input` is `max(width(value), width(placeholder)) + 1` wide and follows its value.
- **The rest of the sheet, and what does not change.** The sheet also gives `table` `wrap: truncate`, `checkbox` and `select` `width: auto; height: auto; wrap: truncate`, and `select > list` `border: single; max-height: 12`. The cross axis (an unsized `col`, `row`, or `box` fills it), `layout: grid` cells, the children of a viewport along its scroll axes, docked children, tables, and every pinned document do not change. In a keymap's `keys`, `ctrl+i`, `ctrl+j`, and `ctrl+m` are `V003` in the current language, since a terminal delivers them as `tab` and `enter`.

### Notes

Clarifications of behavior the SPEC states loosely or not at all (the SPEC itself is not edited; see README.md's "Language notes" section for the same points in more detail):

- **`<text>`/`<button>` body normalization.** Each line of the body is trimmed of XML whitespace (space, tab, CR) and leading/trailing blank lines are dropped; interior spaces are kept. Width and paint both see the trimmed content, so `<text> sync</text>` measures and paints as `sync`, not ` sync`. There is no XML-level way to force a leading/trailing ASCII space through the body (CDATA is trimmed the same way and numeric character references are rejected as V005); U+00A0 (NBSP) and other non-ASCII spaces are not XML whitespace and survive as content, if a literal non-breaking space is an acceptable stand-in. Otherwise use `gap`, `padding`, or `margin` on a parent for spacing. Both points hold for `nowrap` and the `truncate*` values only: `wrap: wrap` cuts a line into words at every Unicode space, so a run of spaces becomes one and an NBSP is a break point painted as a plain space.
- **`{path}` in a `<button>`.** In a `<tui>` without `version`, a button's `label` (even an empty one) or, without one, its body is a template like a `<text>` body: resolved every frame, a missing path is `B003` at the `<button>` and resolves to the empty string, and each LF a resolved value brings becomes a space (line breaks written in a body keep their old behavior). The body of a button that writes `label` is never resolved. An `auto` button is as wide as its resolved label, so it follows its data; write `width` for a steady one. The label is in no event payload, and `tuimark ir` keeps it as written. In a document that writes `version="1"`, `"2"`, or `"3"` it stays literal text and `{path}` is `V003` (`{path} in a <button> label (requires a <tui> without version)`).
- **Form controls: `<checkbox>` and `single`.** In a `<tui>` without `version`, `<checkbox id="dark" bind="settings.dark" label="Dark mode" on:change="dark_changed"/>` paints `[x] Dark mode` or `[ ] Dark mode` (style it with `:checked` and `:focus`; the built-in sheet reverses a focused one). Only `space` toggles it: it writes `true` or `false` to `bind` (without `bind` the runtime keeps the value by `id`) and fires `on:change` with that boolean; `enter` goes on to the keymap, so a form's submit row fires from it, and a keymap row fired while it has focus carries its value. A click toggles it too. Its `label` is a template like a `<text>` body. `single="true"` on a `list` or `table` with `checked` makes `checked` hold one row key, or `null`, instead of an array: a radio group. A focused `single` widget takes `space` as `check-toggle` on its cursor row (choosing the checked row again keeps it), `check-none` clears it, and `check-all` never applies (`B007`).
- **Form controls: `<select>`.** In a `<tui>` without `version`, `<select id="tz" bind="tz" each="zones as z" key="z.id" label="{z.name}" placeholder="zone" on:change="tz_changed"/>` is one row: the chosen option's label (the first option whose key equals the bound value, with its JSON type), or the placeholder, dim, then `▾`. It needs `id`, `each`, and `key` (`V012`, `V017`); without `label` an option shows its key. A bound value that is no option's key is `B012` (a warning) and shows the placeholder. `enter` or `space` (or a click) opens its option list below it, or above it when there is more room there, over the screen and every modal; up, down, home, end, pgup, and pgdn move the list's cursor without writing; `enter`, `space`, or a click picks (writing the key to `bind`, or keeping it by `id` without `bind`, and firing `on:change` with `keys` `{alias: key}` and `value` the key, only when it changed); `esc` closes it; `tab`, `shift+tab`, and `ctrl+c` close it and then act as usual; every other key does nothing while it is open, and a mouse event outside it closes it and is dropped. Closed, it never takes up or down, and `move-*`/`check-*` on it are `B007`. Style the list with `select > list` (the built-in sheet gives it `border: single; max-height: 12`), its rows with `select > list > item` (`:selected` is the cursor, `:checked` the chosen option). A keymap row fired while it has focus carries the chosen key, or `null`, as `value`.
- **Numbers in the store are float64.** The store holds JSON values, so `Bind`, `Set`, `Batch`, `--data`, and the host protocol keep every number as a double: an integer beyond ±2^53 (a snowflake ID) is rounded in `{path}` and `Get`. Pass such values as strings.
- **Built-in defaults beyond §10.6, and `list`/`input` have no border.** This is the built-in sheet of a document that writes `version`; a `<tui>` without `version` changes some rules and adds a focus look (see the defaults of the current language, above). §10.6 only lists defaults for `screen col row box text`; the runtime fills the rest with `scroll`/`list`/`item { layout: column }`, `modal { layout: column; border: single }`, `spacer { flex: 1 }`, `input, button, progress, rule { width: auto; height: auto }`, and `list > item:selected { reverse: true }`. Only `modal` gets a default `border`, so a `border-color` rule on `list`/`input` — a `:focus`/`:selected` variant included — changes nothing unless that element also sets `border: single|double|rounded|thick`. This is why the SPEC §17 inbox fixture's `theme.tcss` (`list:focus`/`input:focus { border-color: $focus; }`) has no visible effect: `dump --styles` and `play --input tab --styles` give byte-identical `styles` regardless of focus. Show focus with `color`/`background`/`bold`/`reverse` instead (a `<tui>` without `version` already reverses a focused `button`, `checkbox`, or `select`; a document that writes `version` writes that rule itself, for example `button:focus { reverse: true; }`), or give the element its own `border: single` first (as `examples/agent`'s `#composer`/`#transcript` and `examples/dashboard`'s bordered panels do).
- **Modal visibility (`open` vs `bind`).** `open` takes `true`, `false`, a bare path, or `!path` (never `{path}`; truthiness is the §7 table). `bind` on a `modal` is shorthand for the same thing: a path whose truthiness opens it. When a modal has both attributes, `open` wins outright and `bind` is ignored for visibility, even when `open` is a falsy path and `bind`'s path is truthy — prefer setting only one of the two on a given modal.
- **Cross-axis stretch inside a modal.** Children stretch to fill the cross axis by default (`align: stretch`) in every language, and an unsized `col`/`row` fills it too. What differs is the main axis and the modal. In a document that writes `version`, `col`/`row` default to `1fr` on both axes and a modal with no size is 80%×80%; in a `<tui>` without `version` a `col`/`row` is `1fr` only directly under a `screen`, a `modal`, or a `tab`, and a modal with no size is as big as its content. A `<row>` of buttons placed inside a `<modal>` (or any column-laid-out ancestor) therefore stretches to the modal's full remaining height, and its buttons stretch with it: always in a document that writes `version`, and in a `<tui>` without `version` only when the modal writes a `height` taller than its content (without one the row is as tall as its buttons). It is most visible when a focused button has `reverse`, which paints its whole rect. Give an action row an explicit `height: 1` or `height: auto` (and consider `justify: center` / `gap` for spacing); `align: start` on the row alone shrinks the buttons but leaves the row itself still filling the height.
- **Focused `list` key handling.** A focused, non-empty `list` (or, in version="2", `table`) consumes `up`, `down`, `home`, `end`, `pgup`, and `pgdn` itself (moving the selection and firing `on:select` on change); these never reach the keymap while the list has focus. `left`/`right` are not consumed and fall through normally. `j`/`k` are never implicit for a list, same as they are not implicit anywhere else (§8.1).
- **List rows are not independently focusable.** Inside `<item>`, nothing takes focus — the list itself is the focusable unit and navigates its rows. Handle a per-row action through the list's `on:select`, or a keymap row scoped with `when="#list:focus"` that reads the event's `keys`/`value` for which row was selected.
- **`Dump` is a side-effect-free snapshot.** It never moves focus, queues events, or mutates scroll/list/input state; `Validate` has the same property. Only the internal frame used by `Run` is "live".
- **`Run` and signals.** On SIGTERM, SIGHUP, or SIGINT, `Run` restores the terminal (cooked mode, main screen, visible cursor) and returns a non-nil error naming the signal, so the process can exit with a failure status instead of exiting clean.
- **Built-in quit.** `ctrl+c` fires the built-in `quit` action when no focused widget or keymap row claims it. With no `On("quit", ...)` handler registered, that action stops `Run`; with a handler registered, `Run` stops only if the handler returns `ErrQuit`. Bind `ctrl+c` in the keymap to route it elsewhere. Under an open modal that routing differs by language: in a `<tui>` without `version` a `ctrl+c` row without a `when` that matches inside the modal does not fire, so `ctrl+c` fires `quit` (write the row in `<keymap when="modal">` to keep it); in a document that writes `version` the row fires as it does outside a modal.
- **Escape latency.** A trailing `esc` byte at the end of a read waits briefly (about 25ms) for more bytes before it is delivered as the `esc` key, so it can be told apart from the start of a longer escape/CSI sequence.
- **Keys of one read.** In a version="2" document each key or paste of one terminal read (or of one `play` `text:` step) is dispatched on a frame rendered again after the previous one changed anything the frame shows (an input's text or cursor, a list or table cursor, an offset, a checked array, a tab), so `when`, `class:NAME` guards, and `if` see it: `text:ab\r` fires an `enter` row whose `when` reads a class the typing turned on, exactly as `text:ab enter` does. A version="1" document keeps the 0.1 loop, rendering again between keys only when events fired or focus moved.
- **A `tabs` whose `bind` path cannot be written** (a value along it is not an object, say `ui.view` with `ui` a number) cannot change its active tab: `switch-to`, `move-*`, `left`/`right`, clicks, and the wheel change nothing there and fire no `on:select`, though a keymap row naming it still takes its key.
- **A dropped mouse event also ends a pending press.** A left release always ends the press before it; a press or release the mouse ignores (outside the top modal, outside the grid, or while `mouse` is false) acts on nothing and leaves no press pending. The wheel over a tab strip with no enabled tab stops there and changes nothing.
- **A viewport without an `id` keeps the offset the wheel gives it.** Only the wheel can move one (it cannot take focus, and `move-*` needs an id), and so it is for a viewport inside a list row or an `each` template, where an id repeats. It keeps that offset under its element and the key of the row it is in, so the offset stays with it when siblings before it come and go and when the rows are reordered; it starts at 0.
- **What `play`'s `events` holds.** It lists the actions dispatched to the host (every `on:*` and keymap host action) and `quit`. The built-in `focus` action and the hyphenated built-ins are carried out by the runtime and never appear themselves: check `focus` in the dump, or the `on:focus`/`on:select`/`on:change` they fire, which do appear. So `<bind keys="t" action="focus" to="#b"/>` shows `"focus": "b"` and, only when `#b` has `on:focus`, that event.
- **A `column`'s `style=""` reaches its header only.** A rule or a `style=""` on a `column` styles its header cell and never its body cells, and nothing warns about it: `<column style="wrap: truncate-middle">` leaves the body cells at the table's `truncate`. Give the column a `class` and style the class (the body cells carry it), or use `#t > item > text`.

- **Composition, briefly.** In a `<tui>` without `version`, `<include src>` places the elements of a `<fragment>` file where it stands, and `<template id>` with `<use template with>` places a copy of a piece of markup with its ids scoped by the use (`U__x`) and its data behind an alias (`with="path as alias"`). The copy is part of the document the dump, the keymap, focus, and events see, so a reusable form field is a template and a long document is split into fragments. Read the v0.4b section above for the rules, limits, and messages, and `tuimark inspect` (`source`/`via`) or `tuimark ir` (`from`) for where a node came from.

## Working on the Tuimark runtime

Everything above (Allowed edits, Forbidden, the Catalog/Loop/Bindings/Actions sections, and the Reference and Notes) is written for UI-authoring tasks: editing `.tui`/`.tcss`/`sample.json` against the runtime as it stands. This section is for the other kind of change: editing the Go runtime itself (`internal/**`, `cmd/tuimark`, or `tuimark.go`).

### Gate

`task verify` runs, in order: the gofmt check (`gofmt -l .` must print nothing — `-l` only lists unformatted files, so empty output is the pass condition), `go vet ./...`, `go test ./...`, the `bin/` build, `./bin/tuimark test`, the js/wasm build with its size budget and a Node smoke test that compares every example's wasm dump with the CLI's (`task wasm-check`, skipped without `node`), and every Glyphrun spec (after a fresh `bun install` of `examples/host-ts`, whose `host_ts*` specs use `@thelacanians/tuimark` from `sdk/ts`). It does not run the race detector, nor the core packages' tests under js/wasm (`task wasm-test`, about a minute, run by CI), so also run `go test -race ./internal/host/` yourself.

```
task verify
go test -race ./internal/host/
```

The manual equivalent, without `task verify` (useful for a faster loop on one piece):

```
gofmt -l .
go vet ./...
go test ./...
task build    # bin/tuimark and every example app the Glyphrun specs run
./bin/tuimark test
task wasm-check
(cd examples/host-ts && rm -rf node_modules && bun install --frozen-lockfile)
glyph run specs/glyphrun/*.yml --format md
go test -race ./internal/host/
```

### Package boundaries

- `cmd/tuimark` — the CLI: flag parsing, output formatting, the golden-manifest runner behind `tuimark test` (including its v0.2a superset check), `tuimark play`'s `--input`/`--script` step parsing and `--frames`/`--strict` wiring (the replay engine itself is `internal/play`, shared with `tuimark test` and `tuimark.Play`), `tuimark inspect` (`Frame` plus `Inspect`), the theme/`:root` token table for `tuimark ir`, the host protocol bridge of `tuimark host` (`host.go`: the fd 3/fd 4 messages with their 64 MiB line bound, the event/reply wait, and the bounded fd 4 queue), `tuimark catalog` (`catalog.go`), `tuimark new` (`new.go`, with the files it writes embedded from `newtemplate/`), the stdlib MCP server of `tuimark mcp` (`mcp.go`, SPEC §15.8), whose tools call the same command code the CLI runs, and the wiring of `tuimark lsp` (`lsp.go`). Parsing, cascade, layout, and paint rules live in `internal/**`.
- `tuimark.go` (package `tuimark`, repo root) — the only public surface: the package functions `Load`, `LoadFS`, and `Parse`, `App`'s methods `Bind, Set, Get, Batch, On, Catalog, Dump, Validate, Play, Run, RunContext, RunWith, Quit, Every, Derive` (SPEC §18, §18.1, §18.2), the `App`, `Batch`, and `RunOptions` types, and the aliases `Event`, `Handler`, `ActionSpec`, `Dump`, `DumpNode`, `Diagnostic`, `PlayEvent`, `PlayFrame`, `PlayOptions`, `PlayResult`, and `ErrQuit`. Nothing else is exported from it.
- `internal/ir` — node/scalar/diagnostic/binding-grammar/key-token types, the tag-kind catalog (`Kinds`, `SpikeKinds`), the spike attribute whitelist (`SpikeAttrs`), and the key-token catalog (`NamedKeys`/`ValidKey`).
- `internal/parse` — the XML tokenizer, the IR builder (including the per-tag attribute catalog, `TagAttrs`), the formatter (`fmt`), IR-as-JSON (`ir`), and composition (`compose.go`, `expand.go`): `<include>` is expanded while the document is built, through a `Loader` the host passes, then each `<use>` is replaced by a copy of its `<template>` (scoped ids, `with` aliases, the use's `class`), and every node carries its `Origin` (the file it is written in and the include or use that placed it).
- `internal/css` — the TCSS parser, selectors, cascade, tokens/themes, and `@media`.
- `internal/layout` — the integer flex engine, with `layout: grid`, the tab strip, and the hint items (`widgets.go`) and the table (`table.go`).
- `internal/paint` — the cell grid, borders, widget painters, and the ANSI frame diff.
- `internal/dump` — the text and JSON frame dump.
- `internal/host` — the JSON store, `Load`/`LoadFS` (a shared `styleResolver` between an OS directory and an `fs.FS`) and `LoadBuffers` (`overlay.go`, `Load` over an editor's open buffers, for `tuimark lsp`), `Get`'s reserved paths and deep copies, `Batch`'s atomic apply, the `Run`/`Play` mode guard (SPEC v0.3 §18.1 rule 8), inflation (`each` on lists and containers, multi-select, table rows with their measure cache in `table.go`), cascade application, focus, the SPEC §8.6 key dispatch with the built-in actions (`dispatch.go`, one procedure for `Run`, `play`, and the hints), tabs (`tabs.go`), hints and sparklines (`hints.go`), the mouse hit test and click/wheel rules (`mouse.go`), events, and the `Run` loop (with the capability/theme probe and `TUIMARK_LOG`), plus `RunHost`, `Run` with the internal hooks `tuimark host` needs (a session-start hook, a stop request, a stop-signal notice) and the fd 3/fd 4 checks (`hostfd_*.go`). A frame is built in the SPEC §18 order: inflate, cascade, tab activation, focus, hints, layout, table rows, paint.
- `internal/play` (v0.3) — the headless replay engine of SPEC §15.4 (`Session`, step parsing): the one place `tuimark play`, `tuimark test`, and `tuimark.Play` apply steps, so their parity holds by construction.
- `internal/agentsdoc` — generates this file from the catalogs above, and the project briefing (`ProjectMarkdown`) that `tuimark new` writes and `tuimark agents --project` prints.
- `internal/catalog` (v0.4a) — builds the output of `tuimark catalog` (SPEC §15.10) from the tables of `internal/parse` (`TagAttrs`, `AttrKeywords`), `internal/css` (`PropertyKeywords`, `PseudoClasses`, `MediaFeatures`), `internal/ir`, `internal/host` (`Builtins`), and `internal/agentsdoc` (the diagnostic table). `schema/catalog.v1.json` validates it, and a test in `cmd/tuimark` compares it with this file both ways.
- `internal/lsp` (v0.4a) — the Language Server Protocol server of `tuimark lsp` (SPEC §15.12), stdlib only: the `Content-Length` framing and JSON-RPC handling (`transport.go`, `server.go`), UTF-16 positions (`position.go`), the open buffers and the debounced `publishDiagnostics` routed by file (`docs.go`, `analyze.go`), and completion, hover, definition, and formatting (`complete.go`, `hover.go`, `definition.go`, `format.go`) over tolerant lexers for a buffer being typed (`lex.go`). It checks documents with `internal/host`'s `LoadBuffers` and `Validate`, the code `tuimark validate` runs, and takes its vocabulary from `internal/catalog`.
- `cmd/tuimark-wasm` and `internal/playground` (ADR 0033) — the runtime as WebAssembly for the website's playground, **private to the website, no compatibility promise**. `internal/playground` is the engine (sessions over an in-memory `fs.FS`, `open`/`render`/`step`/`validate`/`reload`/`close` as JSON calls, mock writes as `tuimark run --mock` does); it has no build tag and uses only the public `tuimark` package, and its tests compare its dumps and `validate` byte for byte with the CLI's for every example and kit component. `cmd/tuimark-wasm` (`//go:build js && wasm`) is the `syscall/js` shim that registers `globalThis.__tuimark`; `testdata/smoke.mjs` and `size.mjs` check the real `.wasm` under Node. GOOS=js is a supported target of the core packages (not of `Run`, which needs a terminal, nor of `cmd/tuimark`): build it with `task wasm`, and test it with `task wasm-test`.
- Application code — `examples/**`, or any external module — uses only the root `tuimark` package. Inside the repo, `internal/layout` is imported by `internal/paint`, `internal/dump`, and `internal/host`; `internal/paint` is imported by `internal/dump`, `internal/host`, and `cmd/tuimark` (for `preview`'s ANSI frame); `internal/play` is imported by `cmd/tuimark` and by `tuimark.go`. SPEC §3 forbids importing `internal/layout`/`internal/paint` from application code outside this repo, not from other packages inside it.

### Hard rules

- The SPEC is the normative specification. It is maintained outside this repository, in the maintainer's notes (`~/notes/projects/tuimark/SPEC.md`): never copy it into the repository, and never change it without the owner's approval. Record interpretations and clarifications as design decisions in the project notes (see "Documentation boundary" below) and, when users need them, in README's "Language notes" and the generated Notes above.
- `testdata/golden/spike/**` is frozen: never regenerate or hand-edit those goldens (`tuimark test --update` skips frozen entries by design). A geometry change there is a runtime regression, not a fixture to update — add a new fixture and manifest entry instead if you need new coverage.
- `examples/inbox/{app.tui,theme.tcss,sample.json}` are verbatim SPEC §17 fixtures: keep them byte-identical to the SPEC's text.
- Closed vocabulary: never invent a tag, attribute, CSS property, unit, or selector. Extending the catalog is a deliberate, catalog-first change (see "Adding things" below), not something a parser special-case should do quietly.
- No Bubble Tea, Lipgloss, `tea.Cmd`/`Update()`, or any other TUI toolkit, as or inside the authoring surface.
- No new dependencies beyond the three ADR-approved ones: `golang.org/x/term`, `golang.org/x/sys`, and, since ADR 0002 (v0.2), `github.com/rivo/uniseg` — used only for grapheme-cluster segmentation; Tuimark's own width function decides column width, ambiguous-width runes fixed at 1.
- Every behavior change ships with a regression test and a design-decision entry in the project notes explaining it (see "Documentation boundary" below).

### Documentation boundary

- `docs/` is the public Tuimark website (Next.js and Fumadocs, tuimark.dev, deployed from `main`). Put only publishable content there: landing page, user guides, public reference, static assets. Its reference pages and screenshots are generated: run `task docs-gen` after changing the CLI, the catalogs, or an example, and `task docs-check` to confirm nothing is stale.
- Design decisions, ADRs, specs in progress, plans, handoffs, review findings, and progress logs live outside this repository, in the maintainer's Obsidian vault at `~/notes/projects/tuimark/` (ADRs under `adrs/NNNN-title.md`, the topic-organized decision record in `design-decisions.md`). Never add them to the repo, and never link public docs to those private paths.
- The SPEC itself lives there too (ADR 0012), not in this repository. The repository keeps only a frozen copy of its §22 block, `internal/agentsdoc/testdata/spec22.md`, for the AGENTS.md prefix test; set `TUIMARK_SPEC` to the SPEC's path to check that copy against the source.
- In the repo, `README.md` is the front page (user-facing clarifications go in its "Language notes") and `AGENTS.md` is generated from `internal/agentsdoc`.

### Adding things

Only when the SPEC itself adds one: SPEC §1 forbids inventing tags, CSS properties, units, or selectors, and SPEC §14 is the single diagnostic taxonomy. These recipes are the mechanics for a change the SPEC has already made, not license to extend the catalog on the runtime side.

- **A diagnostic code.** Implement the check where it belongs (`internal/ir`, `internal/parse`, `internal/css`, `internal/layout`, or `internal/host`), add its row to the `diagCodes` table in `internal/agentsdoc/agentsdoc.go`, add a probe/regression test that triggers it, then regenerate this file.
- **A CSS property.** Add it to `internal/css`'s property table (parsing, `PropertyNames`/`PropertyValues`, and the cascade), add a test in `internal/css`, then regenerate this file so "### CSS properties" above picks it up. `tuimark catalog` reads the same table; if the property is an enumeration, its keywords come from `PropertyKeywords`.
- **A tag attribute.** Add it to `internal/parse`'s `TagAttrs` catalog and whatever in `internal/ir`/`internal/host` needs to read it, add a parser/build test, then regenerate this file so "### Attributes per tag" above picks it up. An attribute that takes literal keywords also needs its row in `internal/parse`'s `attrKeywords` (what `tuimark catalog` lists), which a parser test checks.
- **Regenerating this file.** `go run ./cmd/tuimark agents --repo > AGENTS.md`, then `go test ./internal/agentsdoc`: `TestAGENTSDoesNotDrift` and `TestAGENTSStartsWithSpec22Verbatim` must stay green. Never hand-edit `AGENTS.md`.

### Releasing

A release is an annotated tag `vX.Y.Z` on `main`; `.github/workflows/release.yml` does the rest. Prepare it in a `release-X.Y.Z` branch and a PR, like any other change:

1. **Bump the version everywhere it is written.** `cmd/tuimark/main.go` (`version`, and the `-ldflags` example in its comment), `internal/host/app.go` (`Version`), `cmd/tuimark/version_test.go` (the expected default), `sdk/ts/package.json` (`version`: the release job also sets it from the tag, but `tuimark new --ts` writes `^<the running version>` from the repository copy), and the website's version (`docs/lib/site.ts`, `VERSION`, which the navigation and the landing page read) and its example archive name (`docs/components/install-tabs.tsx`, `tuimark_X.Y.Z_Darwin_arm64.tar.gz`). `TestVersionsAgree` (`cmd/tuimark`) fails while any of them disagree; when one of these files moves, update its `versionMentions` entry and this list together. Then `git grep -n` the previous version for prose that names it as the current one, and leave history alone (CHANGELOG entries, "since vX" comments).
2. **`CHANGELOG.md`.** Turn `## [Unreleased]` into `## [X.Y.Z] - YYYY-MM-DD` with a one-paragraph summary under it, add an empty `## [Unreleased]` above it, and update the link references at the bottom (`[Unreleased]` compares `vX.Y.Z...HEAD`; add `[X.Y.Z]`).
3. **Regenerate and check.** `go run ./cmd/tuimark agents --repo > AGENTS.md`, `task docs-gen`, then `task verify` and `go test -race ./internal/host/`.
4. **Merge, then tag the merge commit.** `git tag -a vX.Y.Z -m "Tuimark X.Y.Z" <merge commit>` and push the tag. The Release workflow runs the behavioral specs, GoReleaser (the archives, the raw per-platform binaries `tuimark_X.Y.Z_<os>_<arch>[.exe]`, `checksums.txt`, the Homebrew cask), then `npm-pack` (embeds the six binaries' SHA-256 in the package) and `npm-publish` (npm trusted publishing from the `npm` environment, which only `v*` tags may use; there is no npm token).
5. **Check that it shipped.** `gh release view vX.Y.Z` lists the six raw binaries; `npm view @thelacanians/tuimark version` is `X.Y.Z`; `npx @thelacanians/tuimark@X.Y.Z version` prints `tuimark X.Y.Z`; the Homebrew cask in `abdul-hamid-achik/tap` names `X.Y.Z`. Never `npm unpublish`: deprecate a bad version (`npm deprecate`) and fix it in the next patch.

### Glyphrun conventions (`specs/glyphrun/`)

- After a deliberate change to a spec's `intent` or `outcomes`, run `glyph spec verify <spec> --stamp` to refresh its `contractHash`; a stale hash otherwise means the contract drifted without review. A spec with no `contractHash` line at all is not checked by this convention (`glyph spec verify` reports `contractHashValid: false` for it but `glyph run` still passes it) — stamp every new spec once its contract is settled.
- Assertions wait for state — `wait: {screen: {contains|notContains: ...}}` or `wait: {process: {exitCode: N}}`, each with a `timeoutMs` — before a snapshot or an outcome is checked. Specs never sleep and hope, but presses whose in-between state doesn't matter (e.g. `press: tab` then `press: down`) are sent back to back with no wait between them. The `preview_watch` fixture script uses `sleep` itself, outside the harness, to space out the file edit it makes.
- `examples/agent`'s specs launch `bin/agent --demo-workspace .glyphrun/ws/<name>` so each spec gets its own throwaway agent workspace; that workspace directory is wiped and reseeded on every run. `.glyphrun/runs/` keeps one timestamped directory per run, pruned to the last `retention.keepRuns`. Both `.glyphrun/ws/` and `.glyphrun/runs/` are gitignored.
- Transient states (a modal mid-open, a progress bar mid-run) are captured with `snapshot: <name>` at the moment they're true and asserted from `$GLYPHRUN_RUN_DIR/snapshots/<name>.txt` in a `script` verifier, not from the live end-of-run screen, which has since moved on.

See `README.md` for the user-facing quickstart, CLI reference, and "Language notes"; the reasoning behind specific interpretation calls is in the design-decision notes described under "Documentation boundary".
